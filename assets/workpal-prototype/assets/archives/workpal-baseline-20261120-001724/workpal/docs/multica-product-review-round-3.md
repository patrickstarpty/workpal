# Workpal 第三轮产品评审

> 后续补充见 [第四轮产品评审](multica-product-review-round-4.md)。第四轮增加 Wakeup、创建草稿、保存视图、分享与快照的组合问题；本轮未解决的问题仍有效，不因出现新报告而视为已修复。

评审日期：2026 年 11 月 19 日。对象为当前工作区，包含行为一致性修复、Squads 更新和新 Analytics 模块。本轮只修改评审文档，没有修改产品源码。

**当前的主要风险是上下文在不同功能之间传递不完整：草稿和最新记录、并行运行与工作流、聊天与项目、快捷操作与接收者、筛选页面与导出报告分别使用了不同规则。单项功能已经明显改善，但组合使用仍可能覆盖数据、发错对象或改变任务范围。**

继续遵循最新 AGENTS.md：Workpal 品牌、英文 UI、Multica 中性紧凑视觉、离线单 HTML、不执行 Skill 安装、不调用真实模型。产品界面不增加 prototype、research、simulation 标签。后端限制及样例数据来源在交付说明中如实说明，不能把样例数值当成实测成果。

## 本轮确认的进展

第二轮指出的多条原始路径已修复，不应重复列作当前缺陷：

- Issue 编辑统一经过 updateIssue，Review 双派发、不启动选项失效和按最新运行误取消对象已有回归覆盖。
- 当前正式交付通过 currentDeliveryId 指定；并行结果可作为 candidate，经人工选择进入评审，取消新尝试不再自动封死旧交付。
- 人工 Done 要求理由；迟到结果不再直接覆盖之后的人工完成。
- Delivery、Review、评论、笔记等表单已保存草稿，上一轮的收起侧栏丢材料路径通过测试。
- 不同标签页追加独立笔记可合并，同记录冲突有导出和恢复入口。
- Chat 的报告解析不再直接写入，任务标题与否定语句的旧错误已有修复。
- Autopilot 模板带验收条件；通知读取包含回复指纹；Saved view 布局、Review note 入口及调度边界已有处理。
- Squad 委派会保存成员、角色和指令快照，头像显示保持一致。
- Analytics 的 Usage、Errors、Teams 使用共享范围查询，基本汇总和响应式布局已通过检查。

这轮发现不是上述修复完全无效，而是修复以后出现或暴露的组合边界。以下 P1 是数据、执行对象或关键工作流问题；P2 是需要修正的交互和产品语义问题。

## 需要优先评估的发现

### T01 P1 旧表单草稿可以静默覆盖另一标签页的新内容

**浏览器已复现，且无需用户在旧表单中输入任何内容。**

1. A、B 两个页面打开同一 Issue。
2. A 打开 Edit issue，查看后按 Escape 关闭，不修改字段。
3. B 修改 Description 并保存。
4. A 刷新，此时模型已经读取到 B 的新 Description。
5. A 再打开 Edit issue，表单却恢复为旧 Description。
6. A 只修改 Priority 并保存，旧 Description 被写回，没有冲突提示。

实际记录显示：打开编辑前，数据为 `New description saved by tab B`；恢复表单后变回原始描述；保存优先级后，持久化描述也变回原始值。

证据：`src/studio.js:50–58` 在关闭或重绘时保存整个表单，不判断字段是否修改；`75–80` 无条件恢复全部旧值。刷新后 storageBase 已是最新版本，因此正常的三方合并无法区分这是有意改回旧值，还是过期草稿误覆盖。

**修复方向：草稿保存用户修改的字段及其编辑基线，而不是整份旧记录。** 未修改的字段读取最新数据；双方修改同一字段时明确比较并选择。未经编辑的表单不应生成可覆盖记录的草稿。恢复时展示草稿基于哪个版本，并提供丢弃草稿入口。

验收：上述步骤最终只改变 Priority，保留 B 的 Description；真正冲突的草稿应提示而不是自动写回。

### T02 P1 保存失败仍提示成功，并清除恢复所需的草稿

**浏览器故障注入已复现。** 本轮没有真的填满用户浏览器存储，而是在隔离上下文中让工作区 setItem 抛出 QuotaExceededError，其余草稿存储保持可写。

操作：填写 Workspace note，然后保存。实际显示 `Note saved.`，持久化 notes 仍为空，原草稿被删除或替换为空表单；刷新后笔记消失。

证据：`src/model.js:171–186` 对普通存储错误返回 false；`src/studio.js:39` 只显示提示但不阻止继续；`818` 的成功路径仍调用 clearFormDraft 和 output，最终成功提示覆盖失败提示。

这比“当前存储不支持同步”更直接：用户被告知已保存，却没有持久化内容。

**修复方向：只有确定保存成功，才能清草稿、关闭编辑和显示成功。** 存储不可用、空间不足、冲突都应作为未保存状态，保留输入并提供导出。模型与界面使用一致的成功或失败结果，不依赖一条短暂 toast 表示持久化失败。

验收：注入失败时，保存动作停留在编辑状态，内容可恢复或导出，没有成功提示；恢复存储后重试可保存同一份内容。

### T03 P1 第一份并行结果会通过 Workflow 提前停止另一方

**隔离 VM 使用当前模型复现，存在正常界面操作路径。**

配置 Review handler 为 Quality；Engineering 是任务负责人；分别启动 Engineering A 和 Quality B。B 先提交产物后，自动成为当前交付并触发 Review 交接。Engineering A 被取消，原因是交给 Quality。

证据：`src/model.js:604–608` 提交当前交付时自动进入 Review；`334–338` 在负责人变化时取消原负责人的活动运行。

这不是第二轮“取消错 Agent”的重复：这次确实取消了原负责人，但用户只提交了并行工作中的一份结果，并没有决定原负责人无需继续。

**修复方向：区分成员结果返回与正式阶段交接。** 有明确并行任务时，第一份结果先进入产物集合，达到约定条件或经人选择后再进入 Review。如果产品选择提交即交接，提交前必须显示将停止哪些运行并允许处理尚未完成的工作。

验收：开启 Workflow 的并行运行与没有 Workflow 的并行运行都能解释第一份产物返回后的行为；不能靠谁先返回决定另一人的工作是否继续。

### T04 P1 Squad 改名后，快捷操作可能发给错误的 Agent

**浏览器已复现。**

创建面向 TAP delivery Squad 的 Quick Action，然后把 Squad 改名为 Delivery team。在 Product partner 负责的任务上执行原快捷操作，系统仍拼接旧名字 `@TAP delivery`。旧 Squad 匹配失败后，评论分发退回当前负责人，最终触发 Product partner，而非 Squad Leader。

证据：`src/studio.js:887–890` 改名迁移仅更新任务、保存视图和 Autopilot；Quick Action 引用没有更新。`944` 通过旧名称拼接评论；`src/model.js:525–534` 找不到明确对象后退回 owner。

**修复方向：接收对象使用稳定 ID，名称只用于显示。** 对于已经选择过的明确接收者，解析失效时应停止并要求重新选择，不得静默发给默认负责人。历史评论保留原始文字，未来 Quick Action 指向同一身份的新名称。

验收：Squad 改名不改变快捷操作的接收身份；删除或失效时明确提示，而不是自动改派。

### T05 P2 Chat 已选择 Project，创建任务表单仍默认另一个项目

**浏览器已复现。**

同一工作区存在 TAP 和 SECOND，将会话 Project 设为 SECOND，输入 `Create issue titled Context check`，生成的任务表单默认 Project 却是 TAP。

证据：`src/studio.js:570–571` 仅传递新任务标题；`183` 的 issueEditor 默认选择显式参数或 db.projects[0]，没有继承当前会话项目。

这会使会话显示的项目上下文与操作目标不一致。表单仍可手动改项目，因此本项没有证明任务已经被不可逆地错建；问题是明确选择的上下文没有成为正确默认值。

**修复方向：动作描述携带明确 scope，包括 Workspace、Project 和相关 Issue。** 显式用户指定优先于会话上下文，会话上下文优先于默认值；如果 Workspace 操作故意不继承会话项目，要在动作卡中说明并显示目标，不能默默选第一个项目。

验收：SECOND 会话的新任务默认属于 SECOND；切换上下文后，旧动作卡仍准确显示自己的目标，不随当前会话悄悄变化。

### T06 P1 Analytics 筛选范围在生成摘要时丢失

**浏览器已复现。测试记录是为检查范围而构造，不是用户工作量测量。**

同一工作区设置 TAP 下两条 Quality 任务，Other 下另有一条。Analytics 选择 Project=TAP、Team=Quality，页面显示两条；从该页生成 Team summary，报告包含三个任务，把 Other 项目也纳入。

证据：`src/analytics.js:146` 仅传 summary|team；`src/studio.js:556` 摘要表单仅有 Team scope；`src/model.js:656` 报告只按 team 筛选。

**修复方向：页面、预览和报告共享同一个范围描述。** 至少保留 Project 与 Team，并在报告中记录筛选范围和生成时间。当前 Issue 状态摘要与一段时间内的 Usage 是不同概念：不要机械套用 Period，应该说明报告反映当前工作状态还是期间用量。

验收：筛选后的页面及其导出引用同一组任务；若用户选择扩大范围，必须在确认界面明确看到变化。

## P2 影响操作连续性和诊断理解的问题

### T07 只修改优先级也会让正常交付变为候选

隔离 VM 已复现：运行期间把 Priority 改成 Urgent，标题、描述、项目和验收条件都不变。提交完整材料后，交付变为 Candidate，Issue 留在 In progress，没有 currentDelivery。

证据：`src/model.js:382–387` 把 priority、team、due、tags 等变化和需求变化共用 operationRevision；`587–591` 用它决定是否为当前交付。

用户可以再手动选择交付，因此不是数据丢失；问题是迟到保护覆盖过宽，日常整理任务也会引入额外判断。

建议分开需求版本、工作步骤版本与行政属性变化。默认情况下，仅优先级、标签或日期变化不应使交付失效；若某字段影响任务执行，应在项目规则中明确。

### T08 Workflow 可以保存没有后续动作的评审自循环

隔离 VM 已复现：把 Review 的完成目标设置为 In review，提交并批准后，Delivery 已批准，Issue 仍在 Review，评审运行已取消，没有下一项待审对象或运行。

证据：`src/studio.js:319` 允许选择任意状态；`src/model.js:642–649` 只校验目标存在，并结束当前评审。

建议禁止没有意义的自循环，或把“另一轮评审”明确建模为新的步骤和评审请求。状态名称合法不代表流程配置可完成。

### T09 Analytics 改筛选后键盘焦点丢失

浏览器已复现：键盘聚焦 Period，选择 7d，页面重建后 activeElement 为 BODY。Project 和 Team 使用相同导航路径。

证据：`src/analytics.js:182` 直接 navigate；指标按钮在 `178–180` 已有焦点恢复，但筛选路径没有。

建议导航完成后恢复同一个筛选控件的焦点和合理滚动位置。验收应是只用键盘连续完成 Period → Project → Team 的操作，不能只检查 selectOption 后数值正确。

### T10 周统计对范围开头的不完整周表达不准确

隔离 VM 固定日期为 2026-11-18，选择 30 天。查询从 10 月 20 日开始，首个周桶却显示 10 月 19 至 25 日，标为完整七天；实际只覆盖 20 至 25 日。

证据：`src/analytics-data.js:118–121` 只判断当前尚未结束的一周，没有判断查询起点对周桶的截断。

总计能够对应，不代表时间表达正确。建议显示实际覆盖日期或天数，同时标记查询开头与结尾的不完整周，避免把覆盖天数不同误读为用量变化。该固定日期用于复现边界，不是本轮实时用量数据。

### T11 updated 表示页面刷新时间，却像数据更新时间

`src/analytics.js:13` 初始化 refreshed 为打开页面的时间，`175` 在点击刷新时改为当前时间，`50` 将其展示为 updated。数据层实际保留独立的 asOf，见 `src/analytics-data.js:132`。

样例历史日期按首次建立时固定，跨日重新打开并没有补充新的历史数据，但仍显示刚刚 updated。

建议区分“数据截至”和“重新计算”。这不涉及增加研究标签或真实后台，只需要准确命名已存在的时间。Multica Analytics 文档也区分统计范围、更新时间与缺失数据，这种口径比增加图表更值得对标。[Analytics](https://multica.ai/docs/analytics)

### T12 Errors 排名不能追溯到组成统计的具体记录

源码确认并结合现有点击路径检查：Top offenders 的 Agent 链接打开普通 Agent profile，后者读取 operational db.runs；Analytics 来自独立的 analyticsHistory.records。当前没有从该排名进入对应历史错误记录的入口。

证据：`src/analytics.js:99`、`127` 与 `src/studio.js:541`。

这是诊断流程缺口，不应通过把样例历史混入任务执行记录来修复。建议提供独立 Usage record 明细，保留 Project、Period、Team、Agent 和错误类别，让用户能查明排名由哪些记录构成。之后才连接适用的排查或处理动作。

验收：用户从某一错误类别或 Agent 排名出发，能看到本次范围内的组成记录，返回后筛选保持一致。

## 产品结构上的三个收敛点

### 把身份和显示名称分开

Squad 改名触发错误路由，说明名称被同时当作身份、显示文案和命令参数。Agent、Squad、Project、Skill 应有稳定 ID，改名不改变关系。无法解析的明确目标不能退回其他对象。

这不需要后台；本地对象同样需要稳定关系。它也为未来 Skill 版本、成员变更、历史归档和项目迁移提供基础。

### 让上下文随动作和产物传递

Chat 的项目、Analytics 的筛选和 Run 的输入快照属于不同类型的上下文，但都需要明确附着到对应动作。不要只依赖当前页面或“第一个项目”这种隐式默认。

建议为用户可见动作保留目标范围，并在执行前或生成前展示。保存后的产物记录其来源范围；后续用户改变当前页面，不应改变既有动作卡和报告的含义。

### 不同变化使用不同版本规则

当前“草稿与最新数据冲突”和“优先级变化使交付变候选”方向相反：前者不够严格，后者过于严格。根源都是没有区分用户修改了什么、它是否影响执行，以及它基于哪个版本。

建议按语义处理：字段草稿基线保护编辑；需求版本保护执行输入；步骤版本保护交接；交付选择保护人工决定；标签、优先级等行政属性单独更新。无需把所有对象做成复杂版本管理界面，但底层关系必须明确。

## 下一轮范围建议

优先修复 T01、T02 的数据保护，再处理 T03、T04 的工作被提前中止或发错对象，以及 T05、T06 的范围传递。之后统一修复 Analytics 时间、键盘和明细追溯，并收紧 Workflow 自循环和版本失效条件。

暂不扩展更多分析图、更多 Agent 配置字段或更复杂 Squad 编排。当前 Analytics 已能展示足够多的信息，下一步价值在于解释和定位；当前任务流已有足够多入口，下一步价值在于它们使用同样的身份、范围和保存规则。

Skill 内容编辑与跨任务方法复用仍属于尚未完成的产品方向，不能因本轮没有再次列出就视为已实现。Multica 将 Skill 作为可维护的方法内容，而不只是外部链接；后续建设应基于稳定身份和版本关系。[Skills](https://multica.ai/docs/skills)

## 测试与证据边界

本轮重新运行的验证结果：

- `npm run check` 通过，57 项测试全部通过，语法检查与离线构建成功。
- Analytics QA 在 1440×900、1280×800、728×900、390×844 通过。
- Drafts QA 在 1440px、390px 通过现有草稿恢复、两标签页笔记合并、冲突导出和工作区隔离路径。
- Squads QA 在 1440px、390px 通过；Consistency QA 通过。
- 新问题通过隔离 VM、独立浏览器上下文或源码路径确认，已在各项注明。T02 是明确的故障注入；未声称用户浏览器实际发生存储耗尽。

TAP Analytics 使用 authored fixture，README 已说明，数据也以 source:fixture 与真实操作记录分离。本报告没有把其成本、Token、失败数当作实测结果，不要求新增研究标签，也不要求接入真实模型或后台。

没有证据证明普通同步调用中的多次 save 必然导致部分持久化，因此没有把该猜测列为缺陷。与之相比，旧草稿覆盖新值、存储失败提示成功、错误目标和报告范围变化都有明确复现。

下一轮应增加组合验收：恢复草稿后再保存其他字段；存储失败后的重试与导出；Workflow 加并行运行；Squad 改名后执行快捷操作；带项目的 Chat 创建任务；筛选 Analytics 后导出；键盘连续筛选和不完整周。单页或单模块测试继续保留，但它们不能替代上述路径。

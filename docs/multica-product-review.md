# Workpal 对标 Multica 产品设计评审

评审日期：2026 年 11 月 18 日。对象为当前 English-first Workpal 原型，即 `src/model.js`、`src/studio.js`、`src/studio.css` 和导出的 `dist/Workpal.html`，不是旧版 `review-v1.html`。

**核心结论：Workpal 已有较完整的对象和页面骨架，但尚未建立可信的工作交付闭环。下一版应围绕任务上下文、执行可见性、交付证据、版本化评审和 Skill 复用重构。继续增加菜单、聊天入口或统计图，不会解决主要问题。**

本报告对 Multica 的判断来自官方文档，不代表对其线上产品的实测，也不推断其实际质量、速度或用户留存。Workpal 的发现来自源码、现有自动化测试、关键模型行为复现及本次 QA 截图。优先级是本次产品评审判断，不是测量评分。

## 产品方向

建议下一阶段聚焦一个明确用户：需要把研发任务交给 Agent，并对交付结果负责的技术负责人或小团队负责人。导师是原型的评审者，不应因此成为产品内部日常工作流的默认用户。

建议产品承诺是：**让团队围绕一项研发工作，把目标、上下文、人和 Agent 的分工、交付证据与可复用方法保存在一起。**

用户打开产品，应能回答七个问题：谁在做、在哪做、用了什么、为什么停、交付了什么、凭什么算完成、下次怎样复用。当前 Workpal 对“有哪些对象”回答较多，对这些问题的回答较弱。

这是一项产品定位建议，后续仍应通过目标用户访谈验证。当前不应同时追求通用聊天工具、Agent 管理后台、Skill 市场、项目管理系统、自动化平台和研究统计平台的完整覆盖。

## Multica 的对标基线

Multica 将 Issue 作为工作的持续记录，将 Agent 视为可复用配置，Runtime 作为执行环境，Run 作为一次触发产生的记录。完成一次 Run 不意味着完成整个 Issue。对 Workpal 最有价值的启示，是保持工作的上下文连续，以及配置、执行和结果之间的可解释关系。[Core concepts](https://multica.ai/docs/concepts) · [How Multica works](https://multica.ai/docs/how-multica-works)

| 能力 | Multica 文档提供的基线 | Workpal 当前状态 | 下一版的设计重点 |
| --- | --- | --- | --- |
| 首次完成任务 | 连接电脑、配置 Agent、创建工作、查看结果 | 空 Workspace 首先要求创建 Project，之后缺少完整引导 | 一条可独立完成的模拟交付路径 |
| Issue | 上下文、讨论、执行历史及交付物集中在工作项 | 有描述、属性、子任务、讨论和 Runs | 以交付和验收为中心组织详情 |
| Project | 为任务提供共同目标及资源 | 主要是描述、负责人、日期和 Workflow | 项目资源及执行上下文预览 |
| Agent | 配置、技能、使用权限、执行环境组成可委派对象 | 有角色、指令、工具、模型和绑定 | 清楚展示适用任务、输出承诺及可用性 |
| Run | 生命周期、失败原因、日志、重试语义 | 有队列、运行、取消及历史 | 统一触发来源、上下文快照和恢复路径 |
| Workflow | 状态进入时的交接、完成及拒绝去向 | 有配置表单，但批准操作存在语义错误 | 展示下一步及其后果，保证执行遵守配置 |
| Skill | 可维护、复用的工作方法 | 以链接目录、收藏和绑定为主 | 内容、版本、来源任务和验证记录 |
| Chat | 面向 Agent 的独立会话与运行 | 本地命令匹配和离线 Agent 队列共用入口 | 发送前明确是本地操作还是模拟委派 |
| Inbox | 与用户有关的工作变化及待跟进事项 | 从订阅任务的活动列表推导 | 可靠的事件通知及直接处理动作 |
| Squad | Leader 负责协调成员 | 能配成员，但执行基本只解析 Leader | 一次可观察的分解、委派和汇总 |
| Autopilot | 可调度的工作及触发记录 | 每日时间、手动触发、创建任务或跳过 | 预演、下一次触发、去重和失败处理 |
| 研发成果 | 项目资源、PR 状态和可打开的环境 | 缺少对应的交付设计 | 用离线样例表达 diff、检查和预览证据 |

对应基线：[Quickstart](https://multica.ai/docs/cloud-quickstart)、[Issues](https://multica.ai/docs/issues)、[Projects](https://multica.ai/docs/projects)、[Project resources](https://multica.ai/docs/project-resources)、[Agents](https://multica.ai/docs/agents)、[Runs](https://multica.ai/docs/tasks)、[Workflows](https://multica.ai/docs/workflows)、[Skills](https://multica.ai/docs/skills)、[Chat](https://multica.ai/docs/chat)、[Inbox](https://multica.ai/docs/inbox)、[Squads](https://multica.ai/docs/squads)、[Autopilots](https://multica.ai/docs/autopilots)、[GitHub integration](https://multica.ai/docs/github-integration)、[Environments](https://multica.ai/docs/environments)。

不能从这些文档推导出“Multica 已有逐条验收的强制证据门禁”或“Multica 能自动合并和发布所有代码”。本报告后面的结构化验收和 Skill 验证闭环，是对 Workpal 的设计建议。GitHub 状态回流与真正执行 Git 操作也应明确区分。

## 应当保留的现有基础

- Issue 与 Run 已区分，结束执行与交付是不同动作；评论触发可以不改变任务负责人。
- 有多次运行历史、按 Agent 去重、取消、退回和继续尝试的基础。
- 页面和聊天卡片使用同一模型，有利于保持状态一致。
- Workspace 隔离、草稿、固定面板、报告快照和本地评审笔记已有实现。
- 离线单 HTML 导出、文本转义、原生对话框及键盘操作已经具备。
- 视觉方向已按用户最新要求更新为对齐 Multica 当前前端：中性浅色外壳、Inter 字体、紧凑列表与统一组件尺寸。具体实现见 design.md。

证据：[模型及运行](../src/model.js)、[交互实现](../src/studio.js)、[现有测试](../tests/workspace.test.mjs)、[构建脚本](../scripts/build.mjs)。这些基础足以支持一次有重点的重构，无需全盘推倒。

## 必须优先修复的可信性问题

P0 表示继续用于产品评审前应处理的误导或核心验收问题；P1 表示下一版主流程必须处理；P2 表示主流程成立后再深化。这里的 P0 不是生产事故等级。

### P0 模拟边界没有进入产品界面

`studio.js:142–147` 使用 Start execution、Submit for review 等动作；`model.js:277–287` 允许直接启动运行；`studio.js:239` 却把所有 Runtime 显示为 Offline。打开独立 HTML 的评审者无法从界面清楚判断哪些是模拟状态、哪些是实际动作。

更严重的是，`scripts/qa.mjs:19` 明确断言页面不得含有 research、simulation、experiments 等词。这与 AGENTS.md 的模拟标识要求冲突，测试正在固化错误的产品承诺。

修复应覆盖常驻模式标识、运行详情、示例证据和导出报告。建议使用 `Interactive prototype · Simulated execution`；模拟动作使用 `Simulate run`。若展示模拟 Online，应标明其为场景状态，不得伪装成真实设备连接。真实保存到本地的用户笔记则准确说明为本地数据。

验收：不阅读 README，用户仍能识别没有真实 Agent 执行；独立导出的报告也保留这一信息。

### P0 当前交付没有可验收的证据结构

`studio.js:143` 的交付主要是一段人工填写的 Handoff note；`studio.js:115` 的验收条件只是文本列表；`model.js:345–373` 没有建立验收条件与交付证据的对应关系。用户写一句话就能进入批准流程。

问题不是原型没有真的修改代码，而是用户无法体验“检查什么才能批准”。下一版应有 Delivery，即一次明确版本的交付，包含变更摘要、产物、验收证据、未解决项和来源 Run。

验收条目至少支持“有证据支持”“未满足”“证据不足”“不适用且说明原因”。不要强制所有工作都提供代码 diff；研究任务可以提交文档和引用，设计任务可以提交方案与操作演示。关键是证据类型符合任务。

### P0 旧交付可以关闭存在新交付的任务

已复现：提交运行 A 的交付，再启动并提交运行 B，返回 A 点击批准。任务变成 Done，但 B 没有评审结论。

`model.js:363–373` 校验运行已交付、未被决定，以及任务处于 review，却没有校验它是否仍是当前有效交付。`studio.js:146` 也会给旧运行提供批准入口。

应把决定绑定到 Delivery ID、交付版本和需求版本。新交付替代旧交付后，旧交付仍可查看，但其批准不能关闭当前任务。若产品允许多个并行交付，需要明确要求批准哪一个交付集合。

验收：A、B 连续交付后批准 A，系统清楚提示“已有更新交付”，且不改变 B 的待审状态。

### P1 工作流配置与实际审批行为不一致

已复现：把 In review 的完成去向配置为 Blocked，提交并批准交付，实际仍进入 Done。Blocked 只是复现时用于检测配置是否生效的目标，不是推荐的业务流程。

`studio.js:183` 允许配置完成去向，`model.js:373` 却对批准硬编码 done。下一版应让按钮直接表达真实动作，例如 `Approve → QA` 或 `Approve → Done`，并通过同一个状态转换规则执行。配置不支持的目标就不应允许保存。

验收：审批遵守配置目标；拒绝遵守退回目标；目标负责人、交接指令和将启动的运行均可预览。

### P1 评论运行与正式交付运行会混淆

已复现：To do 任务先给负责人发评论，生成 queued 的 reply run；随后从 Start run 发起正式工作并选择另一 Skill，实际复用前一个 reply run。完成后没有正式交付，任务仍在 To do。

原因是 `model.js:170` 与 `277–280` 对运行去重的口径不同：页面判断主任务运行时排除了 reply，而按 Agent 查找已有运行时没有区分它。用户看到的动作与系统返回的工作类型不一致。

需要明确：评论是在给运行补充输入、发起独立咨询，还是要求重新交付。任何复用都应显示将加入哪次运行、保留哪些配置；不能静默把正式委派降为回复。

### P1 执行报告混入后来修改的验收要求

已复现：运行完成并生成报告后，修改任务标题与验收条件，再针对同一个 Run 生成报告，新报告使用修改后的条件。

已保存的旧报告本身不会改变。问题发生在生成报告时：`model.js:382–384` 将过去的运行事件和当前任务要求拼在一起，未区分执行当时与当前状态。`model.js:285` 的上下文快照也没有保存需求及验收版本。

应保存执行输入快照，同时可以另列“此后需求变化”。不要把新的要求表现成当时已被验证的要求。

### P1 新回复可能没有重新进入 Inbox

回复存放在旧评论的 `replies` 中，`studio.js:288–295` 的最新活动时间却只读取顶层 `activity[].at`。已经归档的讨论收到 `@Patrick` 回复时，如果没有额外 Agent 日志，仍可能保持归档或已读。

本地行为复现确认顶层通知计算未纳入该回复。由于当前所有发言者都模拟为 Patrick，尚不能据此声称已实测真实多人通知；但设计上已经缺少完整的通知事件来源。

应使用统一的 NotificationEvent，记录事件类型、行为人、目标用户、对象和时间。最小修复也必须纳入回复时间与摘要。自己的动作是否通知自己，应单独定义。

### P1 外部排名没有来源与示例边界

`model.js:82–98` 保存硬编码排名；`studio.js:264–267` 将其显示为 Skills.sh ranking 和带具体日期的榜单。不能因为硬编码就断言原排名一定错误，但当前没有核验记录，也没有标注为示例。

默认排序应优先服务当前项目：适用性、已绑定、团队验证情况。外部热度可作为次级信息；若保留排名，需明确来源、采集时间或示例标签。Local runs 只能表示被记录的使用次数，不能被解释为质量、效果或经过验证的复用次数。

## 功能设计需要怎样重构

### 首页应该帮助用户做决定

`studio.js:45–53` 的首页把一条 Run 放入大幅 Hero，随后展示任务总数等指标。该 Run 按数组顺序选取，未必是最重要的工作。视觉吸引力有了，行动优先级不足。

建议首页按以下顺序组织：

1. Needs your decision：待批准、需澄清、需要人类选择的事项。每条明确“需要你做什么”。
2. Blocked work：等待的输入、设备或前置任务，以及负责解阻的人。
3. Recent deliveries：新交付摘要、证据完整性和 Review 入口。
4. In progress：运行、负责人、最后进展及预计的下一类事件；没有估计依据就不显示倒计时。

数量统计下移，装饰 Hero 缩小或移除。空 Workspace 提供 `Try a sample delivery` 和 `Start with your project`，避免要求用户先学懂全部对象。

### Issue 应成为工作的主要容器

建议详情顶部始终显示目标、当前负责人、任务状态、执行状态和一个主动作。Issue status 与 Run status 分开展示，但用自然语言解释关系，例如“正在等待你的评审；最近一次模拟运行已结束”。

主要内容建议分为 Overview、Activity、Runs、Deliverables。Review 从最新 Delivery 进入，不要求用户先理解 Runs 页面。右侧属性保持简洁，Quick Actions、Wakeups 和子任务逐步展开。

在示例工程任务中，用户应能看到需求、影响范围、交付文件或 PR 样例、检查结果、失败案例和已知限制。多轮返工保留差异及来源，避免每次都从聊天中找结论。

Multica 的 Issue 把讨论、运行与版本化文件交付放到同一工作记录中。Workpal 应学习这种连续性，而不必照搬它的每种列表布局。[Issues](https://multica.ai/docs/issues)

### Project 应提供执行资源

当前 `studio.js:186–190` 仅有描述、负责人、日期和 Workflow。Runtime 配置里虽然有全局工作目录，但它不能替代项目资源及各环境的目录映射。

下一版最小设计应包括：项目目标、Repository 示例、默认分支、参考文档、执行目录映射、适用指令，以及资源是否可用。在 Run 启动前显示“这次实际会使用哪些上下文”。

项目资源的作用是让用户确信任务发生在正确的位置。原型可使用本地示例文本和资源清单，不应添加真实凭据或后台连接。Multica 的 Project resources 将仓库或本地目录与项目关联，这是值得对标的执行边界。[Project resources](https://multica.ai/docs/project-resources)

### Agent 应是可判断是否适用的协作者

`studio.js:392–403` 已能配置角色、指令、工具、模型、Runtime 和 Skill，但用户仍很难判断该 Agent 是否适合当前任务。Access 固定显示 Workspace，也容易被理解为已实现权限。

Agent 页面应优先回答：擅长什么、需要哪些输入、输出什么、哪些决定交给人、目前能否执行。配置区再展示模型、工具和并发。最近成果应可跳到交付及评审记录；样例成果明确标注。

创建流程采用可编辑的角色模板，并提供一次模拟试运行。实际权限控制仍属后续后端范围，但原型应表达“谁可以配置、谁可以调用、权限不足时怎么办”的交互。

### Run 应解释过程和失败

运行详情需要呈现触发原因、发起者、负责 Agent、项目资源、输入快照、绑定 Skill 版本、当前阻塞原因、最后事件、输出和下一步。

离线场景至少覆盖排队、执行、等待输入、失败、取消和完成。失败不能只有一个红色标签；应有可理解原因、保留的成果和针对性的恢复操作。重试必须说明沿用原 Agent/上下文还是按最新配置重新运行。

Multica 文档区分失败原因，并规定手动重试针对原运行的 Agent。Workpal 当前从失败 Run 回到 launch 表单，会按任务当前负责人初始化，因此不应未经解释把它叫作完全相同的 Retry。[Runs](https://multica.ai/docs/tasks)

当前 `run.context` 对部分主任务运行存在，但评论、Wakeup、Chat 使用其他构造路径。下一版应统一创建运行的入口，保证任何触发方式都能回答同样的上下文问题。

### Workflow 应展示行为而非只提供字段

`studio.js:176–184` 逐状态展示负责人、指令、下一状态及退回目标，阅读成本高。建议提供 Engineering delivery 模板，并在配置旁显示具体任务将怎样交接。

保存前预览：进入 Review 后交给谁、收到什么材料、批准走哪一步、拒绝回哪里、已有运行是否停止。停止旧运行应是清楚可见的后果。

Multica 普通改派与 Workflow 交接的停止规则并不相同；后者可让用户选择停止旧运行。Workpal 不必逐字复制，但不能让用户在无提示下失去正在进行的工作。[Assign issues](https://multica.ai/docs/assigning-issues) · [Workflows](https://multica.ai/docs/workflows)

### Chat 应有明确的能力和执行对象

当前所有 Agent 共用 `studio.js:417` 起的本地正则分发。命中命令时即时生成界面卡片；普通自然语言则在 `650–660` 进入离线队列。选择不同 Agent 并不会让这些命令获得不同的角色推理。

建议保留两种清楚的用途：Workspace assistant 处理创建、搜索、筛选、显示报告；Agent conversation 讨论具体问题，并能把已确认的请求转为 Issue。用户应看到项目上下文、所选 Agent，以及当前处于本地操作或模拟场景。

未知输入不应永远排队且没有出路。原型可以明确说明不支持真实推理，并提供“整理为任务”“选择演示场景”“保存草稿”。演示回复必须注明是预设内容。

`Tool events → Surface schema` 有研究价值，但应收进开发者检查入口。默认回复解释采取了什么动作和生成了什么结果；AG-UI、A2UI、MCP-UI 名称不应承担产品价值的解释工作。

### Skill Hub 应形成经验复用闭环

当前 Add skill 主要收集名称、URL、推荐理由和阶段；展示侧强调排名、安装命令、收藏与绑定。它还没有体现团队怎样把一次工作做法变成可复用方法。证据见 `studio.js:254–280`、`733–739`。

建议核心路径为：交付通过评审 → Save as skill draft → 编辑适用条件、输入、步骤、输出与反例 → 关联来源任务和验证案例 → 发布 Workspace 版本 → 绑定另一 Agent → 在新任务中使用。

Skill 详情至少包括内容、作者、来源、版本、适用范围、限制、验证记录、绑定的 Agent 和使用该版本的 Runs。Imported、Draft、Reviewed、Deprecated 是可能的管理状态；Reviewed 必须指向实际人工记录，不能仅靠点击按钮制造“已验证”的外观。

Multica 已把 Skill 视为可维护的内容资产；Workpal 可以进一步把 Skill 与研发交付证据关联，作为有待验证的差异化方向。[Skills](https://multica.ai/docs/skills)

保留 source 和安装命令的文本展示，但不执行安装命令。无需在此阶段建设公共市场、排行算法或真实远程安装。

### Squad 需要一次可观察的协作

`model.js:256–259` 把 Squad 的执行者解析为 Leader；成员与职责配置尚未转成可见的委派计划，Run 上下文也没有完整携带 Squad 方法。

建议先做一个有限示例：Leader 接收任务 → 拆出实现与验证子任务 → 两个成员分别产生结果 → 一项失败导致等待 → 修复后汇总为 Delivery → 人工评审。界面能看清成员、任务、依赖、输出与汇总责任即可。

不要把所有 Squad 任务都强制拆成多个 Agent；简单工作由 Leader 完成也可能合理。需要验证的是有协作需求时，用户能否理解分工及合并结果。[Squads](https://multica.ai/docs/squads)

### Autopilot 应先能预演再能启用

当前只有每日时间和页面打开期间的计时检查；Run only 总是因离线而 Skipped，创建 Issue 模式却能排队。原型范围允许这种限制，但两个模式的行为应在保存前解释。

下一版应显示触发条件、时区、下一次触发、产物落点、上次结果和暂停原因。提供 `Simulate trigger`，先看将创建的工作。还需说明重复触发是否复用任务、上轮未完成怎么办，以及页面关闭期间错过的执行如何处理。

`studio.js:891–896` 只在设备时间恰好匹配时触发，不能据此承诺后台或可靠的周期调度。跨日、重复打开及切换 Workspace 的行为要在规格中定义。Webhook、服务器调度可以延期。[Autopilots](https://multica.ai/docs/autopilots)

### Inbox 和 My work 应覆盖人对 Agent 的责任

当前 My work 在 `studio.js:344` 只筛选 owner 为 Patrick 的任务，委派给 Agent 的工作因此离开“我的工作”。对负责人而言，委派不意味着不再需要跟进。

建议区分 Assigned to me、Delegated by me、Needs my decision。Inbox 则以事件为入口，合并同一任务的变化，突出提及、失败、交付和请求澄清，避免把所有活动都当成同等通知。[Inbox](https://multica.ai/docs/inbox)

### Insights 应支持诊断而非制造效果证明

现有统计能反映本地任务数量，但不能回答哪些工作反复返工、哪里等待人类、什么原因导致失败。未来可按真实事件计算等待时长、返工次数、交付周期及失败类别；每个值应能追溯到对应记录。

在当前原型中，示例图只能标注为示例数据；不能用它宣称提效、成功率或投资回报。优先验证用户能否利用信息做决定，再决定哪些指标值得正式采集。Multica Analytics 对使用量、失败类别及估算成本有明确口径，值得学习其定义和缺失数据表达。[Analytics](https://multica.ai/docs/analytics)

## 信息架构与界面建议

建议把日常工作组织为 Home、Inbox、My work、Projects、Issues；把 Agents、Skills、Runtimes 放在 Team/Resources；把 Automation 与 Settings 保留为次级入口。Chat 可以保留独立入口，但不能承担找不到其他功能时的万能导航。

Run 的主要入口应来自 Issue 和 Agent；全局 Runs 用于排查。Workflow 的主要入口应来自 Project 和 Settings。无需为了减少菜单数量隐藏必要能力，应减少用户完成同一项工作时的上下文切换。

当前双层侧栏、暖色和橙色按钮可保留。需要调整的是视觉优先级：缩小大标题及装饰区，把屏幕空间交给待决定事项和交付证据。Skill Hub 的固定 Impeccable 宣传块不应永久占据首屏，它缺少与当前项目任务的关系。

在 390 像素窄屏上，保留当前无横向溢出的基础。下一版优先让评审、评论、查看证据、处理阻塞可完成；复杂 Workflow 编辑可以分步呈现。每个关键动作需有键盘路径、可见焦点、明确名称和操作后的焦点恢复。

不要把“手机不溢出”当成完整可用性结论。新的证据面板、长任务名、失败状态、空 Workspace、无鼠标路径都要单独检查。

本地 Review notes 应保持易于找到、持久化和可导出。演示场景重置不得清除导师笔记；分享单 HTML 不等于分享当前浏览器数据，这个区别要在导出界面说明。

## 下一版的三条完整用户旅程

### 旅程一 有证据的首次交付

1. 从首页选择预置的 TAP 上传恢复任务，标注为演示场景。
2. 用户确认目标、范围和验收条件，修改内容后形成新的需求版本。
3. 委派卡展示 Engineering partner、项目资源、Skill 版本和模拟 Runtime 状态。
4. 运行进入模拟执行，时间线展示读取上下文、实现和验证等场景事件。
5. 收到 Delivery v1，内含示例变更摘要、测试记录、失败项和验收对应关系。
6. 用户发现“重复上传”证据不足，针对该条件要求补充。
7. 新 Run 产生 Delivery v2，用户能比较 v1 与 v2 并批准当前版本。
8. Issue 进入正确下一状态，保留两次运行、交付及评审决定。

所有结果均为脚本化演示内容，不调用模型、不写真实仓库、不伪装成测量结果。

### 旅程二 从失败中恢复

1. Inbox 显示某项任务等待输入或运行失败。
2. 详情说明原因、已完成的部分、保留的产物和负责人。
3. 用户选择补充信息、重试原运行、按新配置运行或改派；区别在动作前明确。
4. 旧记录保留，新运行链接到前次尝试；若停止原运行，说明后果。
5. 成功交付后通知需要评审的人；读过或归档过的讨论仍能因新相关事件重新出现。

### 旅程三 从交付沉淀方法

1. 从通过评审的上传恢复任务创建 Skill 草稿。
2. 保留来源 Delivery，用户提炼适用范围、必要输入、操作步骤和失败反例。
3. 保存一个带验证案例的 Workspace 版本，并绑定 Quality partner。
4. 在另一个示例任务中选择该版本，运行详情显示其实际被采用。
5. 发现新限制后创建 v2；过去的运行继续指向 v1，避免历史被覆盖。

这三条旅程足以验证产品是否值得继续投入。任意多 Agent 编排、公共 Skill 市场和复杂自动化应排在它们之后。

## 最小数据和状态规格

下面是为支撑产品行为提出的最小关系，不要求把原型改造成生产后端。

| 对象 | 必须保存的信息 | 解决的问题 |
| --- | --- | --- |
| Issue revision | 目标、描述、验收条件、资源引用及版本 | 需求变了之后仍能解释旧运行 |
| Run | 触发来源、参与者、输入快照、执行环境、配置版本、状态及事件 | 任何入口启动的工作都有一致解释 |
| Delivery | 来源运行、需求版本、产物、证据、限制、前一版本 | 明确到底交付了哪一版 |
| Review | 交付版本、逐条结论、评审者、意见、决定时间 | 批准与真实检查对象绑定 |
| Skill version | 内容、适用条件、来源交付、验证案例和状态 | 方法可追溯且可安全演进 |
| Notification event | 行为人、接收者、事件类型、对象和时间 | 回复、失败和交付不会丢提醒 |

需要先固定的业务规则：

- Run 结束、Delivery 提交、Review 通过、Issue 完成是不同事件。
- 任务放弃与成功完成需要区分。当前 Issue 没有 Cancelled 状态，不应为了移出活跃队列而把放弃的工作标为 Done；取消一次 Run 也不等于取消整个 Issue。
- 旧交付不能批准新的需求版本；确需沿用时必须显式确认范围并留痕。
- Workflow 配置、按钮文案和实际状态转换保持一致。
- 运行快照不会随 Agent、Skill、Project 或 Issue 后续编辑改变。
- 同一 Agent 的评论咨询与正式交付运行不会被静默互相替代。
- 改派时旧运行是否继续是明确可见的选择或规则。
- 每条示例执行、交付证据与导出记录保留模拟来源。
- 所有用户输入按文本处理并转义，不因演示 Skill 而执行安装命令。

## 验证与研究计划

本次 `npm run check` 通过：语法检查、14 个测试及单文件构建成功。现有 `scripts/qa.mjs` 使用可用的外部 Playwright 安装运行通过，覆盖离线文件、1440 与 390 像素布局和主要交互。没有真实模型调用。

这些结果说明现有路径可运行，不能说明产品已完成对标，也不能覆盖上文复现的状态问题。旧 `test-results/qa.json` 含旧版测试描述，不应作为本次新版 QA 的依据。

下一轮优先补以下行为验证：

1. A、B 连续交付后，批准 A 不得完成 B 对应的工作。
2. 批准、退回和交接遵循当前 Workflow 的明确规则。
3. 普通评论产生的 reply run 不会吞掉正式执行请求。
4. 修改需求、Skill 或 Agent 后，旧运行输入与旧交付来源保持不变。
5. 新的相关回复使已读或归档任务重新形成可见提醒。
6. 演示执行和报告都带来源标签，取消禁止 simulation 文案的反向测试。
7. 未知聊天请求有清楚解释及可继续动作。
8. Runtime 离线、容量占满、等待输入和运行失败呈现不同原因与恢复路径。
9. 全键盘和窄屏可完成评审、退回、恢复及 Skill 保存。
10. 场景重置、刷新和 Workspace 切换不丢失本地评审笔记。

建议邀请少量目标用户进行无讲解的探索性评审，依次完成三条旅程。记录完成情况、误操作、需要解释的概念、查找证据的路径，以及用户能否正确判断模拟边界。不把这类小样本评审包装为统计显著的效率证明。

最终验收问题是：用户能否在没有讲解的情况下，把工作交出去，判断结果是否可信，处理失败，并让下一次工作复用已确认的方法。只有这条路径成立，更多功能才会增加产品价值。

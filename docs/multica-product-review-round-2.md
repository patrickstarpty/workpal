## 新发现与优先级

这里的 P1 表示下一次产品迭代应优先处理的错误或显著阻断；P2 表示需要明确规则或改善体验的问题。全部属于离线原型当前即可修复的范围。

### R01 P1 并行倒序交付使所有版本无法评审

复现方式：隔离 VM 执行当前模型。

1. Engineering partner 先启动运行 A。
2. Quality partner 后启动运行 B。
3. B 先提交完整材料，成为 Delivery v1。
4. A 后提交完整材料，成为 Delivery v2。

实际结果：v1 因已被 v2 替代不能评审；v2 又因 B 的 Run 编号更大，被判定存在更新尝试。两版都无法批准，也无法要求修改。

证据：`src/model.js:169` 的最新交付按版本选取；`193–199` 的资格判断同时用 Run 编号；`415–418` 按提交到达顺序生成新交付版本。

这是两套“新旧”定义相互冲突。启动时间、到达时间、需求版本、用户选择的有效交付是不同概念。靠再开第三次运行恢复，会迫使用户重复工作。

建议：明确当前接受评审的交付或交付集合。并行成员结果先作为候选产物，由负责人汇总或选择；迟到结果不能自动替代正式交付。历史编号只用作标识，不承担业务有效性判断。

验收：A、B 任意返回顺序都不会导致全部交付失去处理入口；用户能选择接受、合并、保留历史或要求修改，并留下记录。

### R02 P1 进入 Review 会创建错误类型的运行

复现方式：隔离 VM 执行当前模型和从源码提取的原始 saveIssue 函数。

配置 Review 交给 Quality partner；任务负责人是 Engineering partner，状态为 Active；通过 Status 属性改成 Review。

实际先创建 queued review run，随后又创建 queued execution run，并取消刚创建的 review。启动后，任务会从 Review 回到 Active。

证据：`src/studio.js:711–714` 先做 Workflow 交接再做普通派发；`742` 默认给状态属性变更提供 startAgent；`src/model.js:328` 在新 execution 开始前取消 review runs。

建议：一次操作只生成一份派发决定。Workflow 已决定接手者与 run kind 时，普通改派逻辑不得再派发一次。用户看到“进入评审”，结果就应是评审。

验收：该状态变更只产生一次正确类型的触发，不会出现瞬间创建又取消的多余运行。

### R03 P1 不启动选项不能阻止 Workflow 派发

复现方式：同 R02。

给 To do 配置 Agent handler；将该 Agent 负责的 Backlog 任务改成 To do，取消勾选 Start a run when assigning an agent。实际仍创建 queued execution。

证据：`src/studio.js:711` 调用 transitionIssue 时仍允许 handoff；后面的 startAgent 判断只控制另一条分支。`src/model.js:256` 在交接中启动运行。

建议：统一“不启动”的语义，使其覆盖当前操作可能引起的所有派发。若某个流程确实要求强制启动，应在用户操作前说明，并且不要提供无效复选框。

这也是对标 Multica 的明确行为差距：其分配和离开 Backlog 的确认流程提供不启动选项。Workpal 可以采用自己的规则，但界面选项必须兑现。[Assign issues to agents](https://multica.ai/docs/assigning-issues)

### R04 P1 改派会取消错误的并行 Agent

复现方式：同 R02。

Engineering 是任务负责人，先启动 Engineering A，再启动 Quality B；随后把任务改派给 Patrick。实际取消的是较新的 Quality B，Engineering A 仍继续。

证据：`src/studio.js:700–705` 使用 openRun(task.id) 的第一条记录决定取消对象，未限定原负责人；`src/model.js:156` 按数组顺序找到活动运行。

建议：改派前列出受影响的运行，并说明继续或停止的规则。若自动取消原负责人的运行，就按明确身份查找；不能让数组顺序决定取消谁。

验收：两个 Agent 并行时，修改任务负责人不会意外中断另一人的独立工作。

### R05 P1 迟到交付覆盖后来的人工状态决定

复现方式：隔离模型及状态编辑路径。

启动 A 后，用户把 Issue 改成 Done；A 随后提交交付，Issue 被直接改回 Review。

证据：`src/model.js:399` 检查 Run 状态，但不检查它是否仍属于任务当前步骤；`426–430` 无条件把交付推进到 Review。

建议：Run 绑定需求版本和工作步骤。旧运行可以保存迟到结果，但不得静默修改当前任务。提供“查看迟到结果”与“重新接纳为当前交付”的明确动作。

Multica 将 Run 生命周期与 Issue 状态区分开，正常结束不代表任务达标；这也意味着外部结果回来时需要尊重工作项已有的决定。[Runs](https://multica.ai/docs/tasks)

### R06 P1 收起侧栏会清空交付草稿

复现方式：Playwright，在独立浏览器上下文打开导出的 HTML。

打开 running 的正式执行，填写 Summary 和 Artifact content，然后点击 Collapse sidebar。两个输入立即变为空字符串，没有提交、保存或离开确认。

浏览器实际记录：Summary 从 `Unsaved delivery draft with reviewer evidence` 变成空；Artifact 从 `Important artifact draft` 变成空。

证据：`src/studio.js:830` 收起侧栏调用全量 render；`681` 重建 app；`896–898` 只对聊天 prompt 持久化草稿。Delivery、Review 和普通评论输入不在该保存路径内。

这项问题会随着证据表单变长变得更严重。自动化触发也会调用 refresh，说明导航布局与后台更新都不应该重建尚未保存的编辑状态。

建议：按 Workspace、Run、表单类型保存草稿；布局变化只更新布局。草稿持久化失败要明确反馈，提交成功后再清除对应草稿。

验收：收起侧栏、打开聊天、导航后返回、刷新和其他任务更新都不丢失已填写材料；不同运行的草稿不混用。

### R07 P1 多标签页保存会覆盖评审笔记

复现方式：Playwright，同一个独立浏览器上下文的两个页面，均打开同一个 HTML 和 Workspace。

1. 两页同时打开 Settings。
2. A 在 Workspace notes 保存笔记一。
3. B 在 Workspace notes 保存笔记二。
4. 检查持久化记录，只剩笔记二。

两次写入均通过真实界面完成。第一次持久化包含 `Review note to preserve across tabs`，第二次只剩 `Second reviewer note`。

证据：`src/model.js:105–110` 每次把页面内的整个 db 写回 localStorage，没有检测另一个页面更新后的版本。页面 B 的旧内存覆盖了 A 的新数据。

这不是要求实现多人后台。一个人同时打开两个任务页就会遇到，且直接涉及本地评审笔记保护。

建议：为本地数据保存增加修订号和冲突检查，或者对独立记录合并更新。最小版本也应检测陈旧页面并保留本页草稿，阻止静默覆盖，提供重新载入或导出。

验收：两个标签页依次保存不同笔记后，两条都保留；其他任务修改也不能擦除新笔记。

### R08 P1 聊天将标题或否定语句误当作写入命令

复现方式：当前界面路径。

- 输入 `Create issue titled Generate execution report`，实际生成历史 Run 的报告，未打开 Issue 创建表单。
- 输入 `Do not generate a report. Explain what reports contain.`，仍然保存新报告。

证据：`src/studio.js:490–506` 在创建任务解析前匹配 report/summary 关键词，并直接调用有写入副作用的 report()；`726` 在解析消息时执行它。

这已经超出“本地命令理解不够聪明”：用户给标题或明确否定，也会修改 Workspace。更换 Agent 不会改变这条解析规则。

建议：原型优先使用明确的动作入口和参数表单；自由文本先得到可检查的动作草稿。不能可靠判断时，不自动写入。标题、引用与正文中的关键词不能当作新的指令。解析阶段保持只读，确认执行阶段再保存。

验收：上述两个输入分别进入创建任务草稿和非执行解释路径，均不额外创建报告；不能确定意图时，保留原文并给用户选择。

### R09 P1 Autopilot 生成的任务无法直接通过新门禁

复现方式：当前模型调用 triggerAutopilot 并检查生成任务及其执行快照。

自动化创建的 Issue 固定使用 checks:[]，并立即排入 execution；新批准规则要求执行快照必须有验收条件。自动化配置界面又没有验收字段。

结果是自动创建的工作，用户必须先修改需求、取消旧尝试、再开始一次运行，才可能被接受。两个单独通过测试的模块组合起来，默认流程不可完成。

证据：`src/model.js:308–313`、`209`；`src/studio.js:270–277` 的自动化编辑字段。

建议：按任务类型采用合适的交付约定。工程任务可从 Autopilot 模板继承验收条件，摘要或研究任务可定义预期产物和阅读确认。创建时就预览将采用的约定，避免运行完成后才发现无法接受。

Autopilot 的价值是减少重复设置。Multica 将定期发起工作和回到既有 Issue 的 Wakeup 区分；Workpal 也应把自动创建的工作连接到可完成的后续流程。[Autopilots](https://multica.ai/docs/autopilots)

### R10 P1 普通 Done 绕过新评审门禁

复现方式：当前模型及状态属性保存路径。

提交一版没有产物的交付，评审入口拒绝批准；随后通过 Issue 的 Status 属性直接改 Done，操作成功，Delivery 仍未评审。

证据：`src/studio.js:711`、`src/model.js:235`。状态转换只检查状态名称，未区分正常交付接受与人工完成。

人工直接完成任务不一定错误。当前缺陷是产品既声称通过交付门禁保护验收，又在另一入口无提示生成相同的 Done 结果。

建议明确提供两种行为：Accept delivery 和 Complete manually。需要验收的项目中，人工完成必须记录理由及未完成的评审；其他轻量任务可正常完成。统计和时间线不能把两者混为同一种已验证成果。

验收：允许的人工例外清楚可见、可追溯；不允许的例外在状态编辑和看板拖动中也不能绕过。

### R11 P2 保存视图的布局不能可靠恢复

复现方式：界面保存 Board 视图，从 Saved views 打开，显示为 List。

证据：`src/studio.js:845` 的 applyView 设置 layout 后，进入路由时 `984` 又按 issuePrefs 覆盖它。

建议先定义三个层级：保存视图的默认布局、当前用户在该视图上的覆盖、页面全局偏好。没有该视图的个人覆盖时，应恢复它保存的布局。

验收：保存 Board 及筛选条件，离开后重新打开，布局和筛选同时恢复。

### R12 P2 标为已读第一次点击可能无效

复现方式：一条曾读过的任务收到新的顶层活动，按钮正确显示 Mark read；点击后仍 Unread。

证据：Inbox 用 readAt 与 latest 比较判断是否未读，但 `src/studio.js:834` 仅判断 readAt 是否非零来切换。旧时间戳非零，新点击反而设成 0。

建议按钮执行它显示的明确命令。Mark read 写入当前已读位置，Mark unread 清除，不依赖模糊布尔切换。通知读到哪个事件，最好按事件序号而非时间戳表示。

上一轮“嵌套回复没有纳入最新通知时间”的问题也仍在，建议与本项一起改为事件驱动。

### R13 P2 取消新尝试后没有恢复旧交付的路径

复现：A 已交付且可评审，创建 queued B 后立即取消。A 仍被禁止批准和退回，即使 B 从未开始。

证据：`src/model.js:196–199` 只要有更大 Run 编号就阻止；`tests/workspace.test.mjs:340` 明确将这个策略固定为测试要求。

这是一项已实施的保守产品策略，不能简单当成漏写判断。需要补的是恢复能力：若新尝试未执行且需求未变，可明确放弃 B 并恢复 A；若已产生影响，则说明为何需要重新交付。用户误点后不应只能重填所有材料。

### R14 P2 配置和模型中存在界面无法兑现的行为

两处具体问题：

- Workflow 编辑器允许设置 Active 的 When done, move to，但 `src/model.js:428–430` 强制所有交付进入 Review。配置可保存却不会生效。若强制评审是产品规则，应重新命名或收起该字段。
- 模型与 `tests/workspace.test.mjs:421` 支持 review run 保存 Review note，但 `src/studio.js:185` 只提供打开交付、结束和取消，没有保存评审发现的表单。测试覆盖了用户无法到达的能力。

Multica Workflow 通过步骤、接手者和完成/拒绝去向描述协作。Workpal 可以简化，但必须让每个可编辑字段都对应可观察的行为。[Workflows](https://multica.ai/docs/workflows)

### R15 P2 切换 Workspace 会使另一空间的定时任务错过触发

源码确认：`src/studio.js:988–995` 的定时器只检查当前 db.autopilots；切换 Workspace 会替换 db，且触发判断只比较当前分钟，没有补偿。界面在 `277` 描述为 Enabled while Workpal is open，范围比实际行为更宽。

因此，即使 Workpal 页面一直打开，用户在另一个 Workspace 工作时，原空间的自动化也不会被检查。这项结论来自执行路径分析，本轮没有通过等待真实时钟跨分钟进行浏览器计时测试。

建议明确当前空间活跃时才检查的限制，或在页面打开时检查所有本地 Workspace，并定义错过触发后的处理。无需实现服务器调度，但工作空间切换不应悄悄改变用户对调度的理解。

## 产品建议需要进一步收窄

### 将交付证据与任务类型关联

上一轮建议强化证据是合理方向，但不应推导成所有任务都必须经过同一张长表单。当前每次正式执行都要求用户手填摘要、产物和逐条证据，既增加录入负担，也使 Autopilot 默认任务走不通。

建议使用可解释的工作约定：工程变更需要验收证据；调查需要结论、依据与未决项；普通咨询可以只回复；例行摘要需要符合模板的产物。项目可以选择严格程度，提交前预览缺失项。

这并不要求真实模型或自动生成材料。原型可以根据已有任务和用户输入提供结构化编辑、从历史材料复制并注明来源，但不能编造测试结果或 Agent 回复。

### 明确三种不同的产品身份

当前界面让同一个人创建任务、填写 Agent 产物、执行评审，再把 Run 称作 Walkthrough。这适合内部验证，却让面向用户的产品行为混入了实现过程。

界面应表达委派者、执行者、评审者各自的职责。当前本地操作者可以录入所有材料，但记录应准确说明作者和材料来源，不能自动把人的文字归为 Agent 生成。身份权限仍可在交付说明中声明未实现。

按照最新方向，Offline walkthrough、Walkthrough in progress 和反复解释没有执行代码的长说明应移出主流程，放入交付说明。Runtime 的 Offline、Unavailable 等真实状态仍可保留；它们帮助用户判断能否执行，与研究标签不是一回事。

### 让进度反馈服务当前决策

新版已经转为中性紧凑风格。下一步无需继续大量微调圆角和灰度，应把交付页的阅读顺序调整为：当前状态及主动作 → 交付摘要和缺口 → 产物与证据 → 评审发现 → 历史输入及技术记录。

目前 Run ID、离线说明、输入快照等先占据空间，重要表单或证据需要继续滚动。先让用户知道“这次需要我检查什么”，再允许展开完整快照。工作流字段和诊断 JSON 都应保留，但不宜成为日常路径的主体。

### 从可配置转为可预期

当前不少字段能填写，却不能稳定预测结果：startAgent、Active.next、Saved view layout 都存在这种问题。功能完整度不应按字段数量评价。

每个配置应回答三个问题：它影响哪次操作、何时生效、已开始的工作是否受影响。保存后用具体任务预览实际后果，比继续增加配置项更重要。

## 下一轮建议的实现边界

建议先做一次有限的行为一致性修复，不继续扩大功能面。

1. **统一操作后果。** 创建、改派、状态变更、Workflow 交接先产生同一份操作计划：任务变化、启动哪些运行、取消哪些运行、通知谁。界面展示后果，模型执行同一份计划，消除双派发和错误取消。
2. **明确有效尝试与有效交付。** 用显式关系记录 replacement、candidate、accepted-for-review；保留迟到结果，避免用 Run ID 或到达顺序代替业务规则。
3. **保护编辑和保存。** 完成交付/评审/评论草稿，布局变化不重建输入；本地数据保存检测跨标签页冲突，先保证评审笔记不丢失。
4. **打通组合路径。** Autopilot 创建的任务能完成；Review handler 能记录发现；不启动选项覆盖 Workflow；人工完成作为显式例外；聊天解析只读。
5. **修复日常可靠性。** Saved views、Mark read、恢复旧交付及表单恢复等小动作必须稳定。它们会比更多高级功能更频繁地影响使用。

Skill 内容/版本、项目资源、Squad 成员协作仍值得建设，但应接在稳定的任务生命周期上。否则它们会继承当前状态与结果归并问题。

## 本轮验证范围和下一轮验收

本轮重新运行并通过 `npm run check`：28 项测试、语法检查与离线构建均通过。`scripts/qa.mjs` 和 `scripts/delivery-qa.mjs` 也通过，覆盖 1440px/390px 的现有路径。这里没有把实现说明中旧的五尺寸布局结果冒充为本轮新运行。

新增问题通过源码、隔离 VM 或独立 Playwright 浏览器上下文复现；草稿丢失和多标签页笔记覆盖均使用真实界面操作。没有触碰用户现有浏览器评审数据，没有真实模型调用，也没有执行 Skill 安装命令。

测试通过仍不能替代这些组合场景。下一轮需要以下行为验收：

- 一个状态操作至多派发一次正确类型的运行。
- 不启动选项对所有派发来源一致有效。
- 改派不会停止无关的并行工作。
- 并行运行任意完成顺序都有明确可评审的结果。
- 迟到结果不能静默覆盖人工之后的决定。
- 收起侧栏、导航和其他记录更新不丢失编辑内容。
- 两个标签页保存的不同评审笔记都存在。
- 标题和否定语句不会触发错误的报告写入。
- Autopilot 的默认输出能走完所选交付约定。
- 手工 Done 与接受 Delivery 有可区分的记录。
- 保存视图恢复正确布局；Mark read 一次即生效。
- 每个可配置的完成去向和每个受测能力在界面中可观察、可到达。

下一版应让用户能够预测操作后果、保住输入、处理迟到与并行结果，并恢复一次误操作。它们是当前 Workpal 从可演示走向可用产品设计的必要条件。

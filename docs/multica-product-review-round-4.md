## N01 · P1 · Done 没有结束未来委派

**证据：隔离 Playwright，通过现有 UI 操作，使用浏览器时钟推进。**

1. 在 TAP-030 上建立一分钟后的定时 Wakeup。
2. 通过 Status 属性将 Issue 改为 Done，填写人工完成理由并保存。
3. 推进浏览器时钟 75 秒。

结果为：Issue 保持 `done`，Wakeup 变成 `Triggered`，产生 `RUN-016`，状态为 `queued`、类型为 `reply`。任务已经结束，未来委派却还在发生。Done Issue 仍显示 Add Wakeup，提交时也没有终态限制。

源码：`src/model.js:348–350` 写入状态，没有结束既有 Wakeup；`src/studio.js:484–492` 触发检查只判断任务存在；`:480` 与 `:860–863` 的创建入口和提交没有检查 Done。

这与第三轮的迟到交付问题不同：迟到交付是已开始工作如何返回；这里是任务完成后仍启动新的后续请求。

Multica 明确把 Wakeup 绑定到 Issue 生命周期：Done/Cancelled 会停用规则，并撤回尚未开始的相关运行；重新打开任务不会自动恢复旧规则。[Issue wakeups](https://multica.ai/docs/issue-wakeups)

**建议：把完成任务定义为一次完整操作。** 写入完成记录时，同时结束等待中的 Wakeup；创建时与触发前都检查终态。已经运行的工作如何处理应明确显示，不能用“Done”默默推断所有运行都已停止。重新打开任务时，让用户明确选择是否重新建立规则。

验收：Done 后推进时间、追加评论、完成子任务，均不能触发旧规则；重新打开后旧规则保持停用；需要继续工作时可明确创建新的 Wakeup。

## N02 · P2 · 规则已触发，屏幕仍允许“取消等待”

**证据：隔离 Playwright，通过现有 UI 操作，使用浏览器时钟推进。**

新建一分钟后的 Wakeup，停留在 Issue 页面并推进时间。数据库中已经是 `Triggered`，关联 Run 已 `queued`；屏幕仍显示 `Product partner · Waiting`、Cancel 和尚无首个 Run 的空态。

点击残留 Cancel 后，规则被写成 `Cancelled`，Run 仍为 `queued`；Activity 同时保留 `Wakeup triggered`。用户无法从“Cancelled”判断到底取消了什么。

源码：`src/studio.js:496` 触发后只保存；`:1116–1120` 计时器没有针对 Wakeup 变化刷新页面；`:955` 的 Cancel 不检查当前规则状态，直接改写为 Cancelled。

**建议：让界面展示最新事实，并为取消动作定义边界。** 到期后更新状态、关联 Run 和操作按钮，同时保留正在填写的评论、草稿及焦点。提交取消时再次检查状态，不能仅相信旧按钮仍在屏幕上。

若规则已经触发，展示“已触发”和关联 Run；如果提供撤回待运行请求，应明确处理该请求。关联 Run 可能还承载其他工作，不能简单取消整个 Run 而误伤原任务。规则的历史触发事实也不应被覆盖。

验收：到期后无需刷新就能看到 Triggered；旧 Cancel 请求不会把触发历史改成“成功取消”；对 queued 与 running 的处理和提示可以区分。

## N03 · P2 · 在另一个项目创建任务，旧草稿会换掉目标项目

**证据：隔离 Playwright，已实际提交并检查持久化任务。**

1. 在 TAP 项目打开 New issue，填写标题、选择 Backlog，关闭表单。
2. 在 SECOND 项目点击 New issue。
3. 表单恢复为旧标题、Project=TAP、Status=Backlog。
4. 直接提交，实际生成 `TAP-035`，`project=TAP`、`status=backlog`。

同一草稿从看板的 New issue in To do 入口打开，也仍恢复成 Backlog。这里不仅是默认值不理想，已经验证可以造成任务错建项目；任务仍可编辑，不是不可逆数据丢失。

源码：`src/studio.js:62–67` 所有新任务使用相同的 `issue|` 草稿键；`:91–92` 无条件恢复；`:193–204`、`:535–536` 的项目或状态入口没有成为草稿身份的一部分。

它与 T01 的多标签旧记录覆盖、T05 的 Chat 默认项目不同。本项只需一个标签页，是多个“创建任务”入口共用草稿导致的碰撞。

**建议：草稿属于一次明确的创建意图。** 至少识别 Workspace、Project、Parent、入口指定的状态及独立草稿 ID。进入 SECOND 的创建动作，应保留 SECOND；如果发现 TAP 的未完成草稿，提供明确的“继续 TAP 草稿”入口，而不是替用户改变目标。

验收：项目、看板列、子任务和通用新建入口互相切换时，目标项目、父任务及指定状态不被其他入口的草稿覆盖；用户输入仍能找回，不能靠删掉草稿解决。

## N04 · P2 · Saved view 没有可辨认、可恢复的身份

**证据：隔离 Playwright，包含导航和刷新。**

八条任务中筛选 Patrick，得到一条，保存为 Only Patrick 后应用。URL 仍为 `#tasks`，页面仍叫 All issues。隐藏过滤栏，进入 Overview，再点 All issues，仍只显示一条；刷新同一个 URL，又变成八条。

这使“我现在看的是全部任务还是一个视图”无法从页面名称和地址判断。隐藏筛选栏进一步使范围不可见；刷新又不能恢复刚才看到的范围。

源码：`src/studio.js:47` 使用内存过滤变量；`:297–303` 应用过滤；`:964` 的 applyView 只赋值并进入普通 tasks；`:741–742`、`:1105–1110` 没有恢复 Saved view 身份。

**建议：Saved view 是有名字和地址的对象。** 应用后展示 Only Patrick，并在路由中记录视图身份。对视图的临时修改要可辨认；All issues 进入基础范围。即便隐藏筛选编辑器，也保留当前筛选摘要、结果数量和清除入口。

验收：刷新、后退、复制链接和重新进入都能解释并恢复范围；从侧栏进入 All issues 不再悄悄沿用某个视图的过滤。

## N05 · P2 · 保存过的看板会被后来隐藏的列变成空白

**证据：隔离 Playwright。**

保存一个有一条任务的 Todo Board；之后隐藏 Todo 列，再应用原视图。结果显示零条，Todo 列没有恢复。任务并没有被删除，只是被当前全局显示配置遮住。

保存对象只有 `status/owner/query/layout`；全局 `issueDisplay.hidden=['todo']` 继续生效。源码：`src/studio.js:305–310`、`:881`、`:964`、`:992`。

这不是第二轮 R11 的“Board 恢复成 List”重现；布局类型已经恢复，但决定能否看见结果的列配置没有恢复。

**建议：明确哪些显示选项属于视图，哪些属于个人偏好。** 隐藏列会改变可见结果，应随视图保存；若刻意保留全局隐藏，必须显示“还有 1 条结果位于隐藏列”和恢复操作。不能只用一个无结果空态掩盖真实命中。

验收：保存视图后改变其他页面列设置，再次打开原视图，结果仍可发现；空态区分“没有匹配任务”与“匹配任务被隐藏”。

## N06 · P2 · Share skill 分享了说明，没有分享可用内容

**证据：两个相互隔离的浏览器上下文，均打开同一离线 HTML。**

A 通过 Add skill 新增 `Release Gate Checklist`，点击 Share skill，复制结果为：

```text
Release Gate Checklist · https://example.com/release-gate
Open the shared Workpal.html file and select Release Gate Checklist in Skill Hub.
```

B 打开同一份 HTML 后没有该 Skill；访问对应详情显示 `Skill unavailable.`。这是自定义记录的问题，内置 Skill 的查找路径仍可成立。

源码：`src/studio.js:915–921` 只写入 A 的本地目录；`:996` 只复制文字，没有携带记录或导入入口。`src/model.js:30`、`:45–51` 在接收方初始化内置目录。

**建议：先让按钮的承诺成立。** 如果只复制外部来源，叫 Copy source，说明接收方可打开来源；若叫 Share skill，则交付可导入记录或包含它的离线文件，并处理同名冲突与来源信息。无需真实发布后端。

更长期的产品差距仍然存在：Multica 的 Skill 包含可维护的 SKILL.md 和支持文件，可附加到 Agent，后续修改影响后续 Run。Workpal 当前主要提供目录推荐和绑定，尚不能把“分享外链”当成“复用团队方法”。这属于此前已识别的产品方向，本轮只新增确认分享按钮的具体断点。[Skills](https://multica.ai/docs/skills)

验收：接收方从分享内容出发，不依赖发送方 localStorage，能查看同一份方法说明和来源，再决定是否添加；没有携带内容时，不能声称它已在接收方工作区中。

## N07 · P2 · Runtime 改配置后，历史运行无法还原原目录

**证据：隔离 VM 使用当前模型复现；注册 Runtime、绑定 Agent、启动 Run、修改 Runtime 均有界面入口。未声称在该目录执行过代码。**

注册 Dev laptop，目录设为 `/workspace/customer-a`，绑定 Engineering partner 并创建 Run；之后把 Runtime 目录改为 `/workspace/customer-b`。旧 Run 的 `inputSnapshot.context.runtime` 只有 `RUNTIME-001`，完整快照及 Execution report 都不包含原目录，设备名称和平台也没有完整留存。

源码：`src/studio.js:391–398` 收集配置并绑定，`:882–883` 覆盖 Runtime 记录；`src/model.js:494–502` 只保存 Runtime ID；`:246–250` 未补充配置对象；`:654–666` 报告导出同一不完整快照。

**建议：Run 同时保存身份引用和启动时配置。** 复制当时的 Runtime 名称、平台、工作目录，展示为当时配置的执行范围。之后改设置只影响新 Run。当前离线阶段不必验证目录存在，但不能丢掉用户原先选择的上下文。

验收：修改 Runtime 后查看旧 Run 和其新生成的报告，仍能读到 customer-a；新 Run 使用 customer-b；两者都不被误写为实际执行证据。

## N08 · P2 · 搜索快捷键打开了窗口，没有开始搜索

**证据：隔离 Playwright 键盘操作。**

按 Cmd/Ctrl+K 后，焦点在 Close dialog，直接键入搜索词不会进入查询框。用户还需要额外 Tab 才能开始搜索。

源码：`src/studio.js:571` 的搜索表单没有初始焦点约定；`:746–748` 将关闭按钮放在首个可聚焦位置并直接 showModal；`:1073` 附近快捷键只负责打开弹窗。

**建议：打开搜索后聚焦查询字段，保留需要继续编辑的搜索词；结果刷新后维持可操作的焦点。** 关闭弹窗应回到原入口。这里与第三轮 Analytics 筛选焦点丢失是不同路径，但适合统一制定弹窗和重绘的焦点规则。

验收：仅用键盘完成快捷键 → 输入 → 选择结果 → 返回 → 再次搜索，无需先寻找查询框。

## N09 · P2 · 默认主题偏离当前明确约束

**证据：源码及全新浏览器上下文。**

没有 `workpal.theme` 存储时，实际 `data-theme='warm'`，前景色为 `#183028`，品牌色为 `#a8460c`。手动选 Neutral 后可以保存并在刷新时恢复，说明切换本身有效；问题是首次打开的默认方向。

源码：`index.html:2` 默认 Warm，`src/studio.js:9–10` 对未设置偏好也选 Warm；CSS 末尾加入琥珀色与深绿色覆盖。当前 AGENTS.md 明确要求 Multica 中性表面，并说明早期 TAP 配色方向已被替换。

**建议：Neutral 作为无偏好时的默认值。** Warm 可以保留为可选主题；不要把有可选 Neutral 当作已经满足默认视觉方向。此项是与当前明确约束不一致，不是认定暖色本身品质较差，也未做 Multica 在线产品的逐像素比较。

验收：全新存储、无效偏好、存储不可用时均落到 Neutral；用户明确选择 Warm 后可以保留其偏好。恢复默认不应清除工作区记录或评审笔记。

## 要做成好产品，下一版需要交付什么

Multica 文档区分持续推进的 Issue 和一次执行的 Run，明确完成 Run 不代表完成 Issue。Workpal 已开始建立这套结构，本轮说明同样的严格程度还没有延伸到 Wakeup、草稿、视图和分享。[Runs](https://multica.ai/docs/tasks)

下面是针对 Workpal 的产品建议，不是宣称 Multica 已实现每一项建议。

### 第一批：先修复数据和完成语义

把第三轮 T01、T02 放在最前：用户保存过的内容不能被无提示覆盖，保存失败不能被报成成功。并行处理 N01、N02，让完成任务和取消后续请求的结果准确可见。

这一批的交付标准不是“按钮可以点击”，而是用户离开页面、刷新或等待一段时间后，事实仍与操作承诺一致。涉及取消时，明确区分停止规则、撤回排队请求、停止已经开始的 Run。

### 第二批：统一动作的目标与当前范围

将 N03、N04、N05 与 T04、T05、T06 放在同一批处理。创建入口、草稿、已选接收者、保存视图及报告，都应携带明确的目标和范围，而不是读取此刻碰巧生效的页面变量。

用户应始终能回答：我在哪个 Workspace/Project；我正在处理哪一批 Issue；动作会交给谁；刷新后是否还是这批对象。对象名称变化可以改变显示，不应改变身份。视图可以调整显示，不应让有结果与无结果无法区分。

### 第三批：让方法分享真的跨过发送方边界

先修正 N06 的当前承诺，再完成一个小而完整的 Skill 复用路径。不要以新增更多目录条目代替方法内容。

建议选一个明确场景，例如 Release readiness review：从已经交付的检查方法中整理目的、输入、步骤、输出和验收；保存版本和来源；分享给另一个独立工作区；接收方可检查后添加；下一次 Run 引用该版本；报告能说明使用了什么方法和配置。离线记录也能完整表达这条路径，不需要制造真实 Agent 成果。

N07 的 Runtime 快照应与这一批一起补齐：方法、任务和配置共同解释一次尝试。单独保存一个 Skill 名称或 Runtime ID，不足以支持后续复盘。

### 下一版交付前的六条端到端验收场景

1. **创建不串范围：** 在 A 项目留下草稿，进入 B 项目或另一看板列，创建目标仍正确；返回时 A 草稿仍可找回。
2. **完成能够结束等待：** 有时间、回复、子任务 Wakeup 的任务进入 Done 后，后续事件不再排队旧请求；重新打开也不默默恢复。
3. **取消能够解释结果：** 到期前取消、触发瞬间取消、排队后撤回和已经开始后的停止，都能看到准确事实及受影响对象。
4. **视图能够重现：** 命名视图经过列隐藏、切页、刷新、返回后，命中范围可恢复；隐藏结果有解释。
5. **分享能够被接收：** 第二个独立浏览器只拿到分享产物，也能查看并添加自定义 Skill，不依赖发送方存储。
6. **历史能够解释：** 修改 Agent、Runtime 或 Skill 后，旧 Run/报告仍保留当时输入；新尝试清楚使用更新配置。

快捷键和默认主题作为这一轮基础体验修复完成，不建议另开一次大规模视觉重构。当前主要收益来自让已有功能的承诺可靠。

# Workpal 软件开发协作平台设计

状态：待用户评审。用户已选择统一工作平台与独立执行端方案，尚未批准本设计文档。

本稿以本地 Multica 来源文档为功能基线，定义面向软件开发团队的 Workpal 完整能力和分期边界。后端使用 Python；保留 Workpal 品牌、English UI 与当前 Multica 视觉体系。现有原型仅作为交互参考，不直接修改。本文是待评审设计，不代表功能已经实现。

## 意图与已确认决策

用户希望 Workpal 用于软件开发，同时支持人管理工作与 Agent 真实执行。软件需求、设计、编码、测试、评审和交付形成统一记录；开发者仍可使用外部工具，并将实际产物纳入同一流程。

已确认：首版支持 SIT、UAT、PRD 等真实环境故障调查、原因与方案回答、Jira 缺陷创建及关联修复；日志、监控与发布记录的数据源暂未确定，采用可配置适配器，实际接入前再确认；用户可通过 Chat 用自然语言调用 Agent，完成自己在 Workpal 中有权限手工完成的全部操作；首版包含真实开发交付、独立 Chat、可配置复杂工作流、自动化及本文核心协作能力，内部可分批实现但不将这些能力推迟到后续版本；功能参考 Multica 来源文档；后端 Python，平台数据先统一放 SQLite；代码托管支持 GitHub 与 ADO Repo（Azure Repos Git）；采用统一工作平台与独立 Runtime；原型以普通文件保存在 assets/archives，不打 ZIP，不直接修改。English UI、Workpal 品牌和现有视觉体系延续项目约束。

成功标准是团队可以从一条有验收标准的需求出发，让人或 Agent 完成仓库修改，提交真实测试证据和 PR，经过评审、返工后形成可追溯的结果；不是页面数量或 Agent 数量。

本文中的首期部署、默认权限、触发政策、数据保留和发布边界是设计者建议，供本次文档评审确认；不将其描述为用户已决定。

## 目标与边界

目标：统一开发协作、真实执行、可靠恢复、证据评审、可复用 Skills。人工执行和 Agent 执行使用相同交付对象，来源身份分别记录。

首个可用版本必须包含真实改代码、执行测试和创建 PR；建设顺序可以先做记录服务，但不能以只有任务管理的版本宣布完成。首期面向一个可信的小型团队、GitHub 和 Azure Repos Git 两种仓库接入（每个验收场景使用一个仓库）、一台团队自有 Runtime 和一种已安装且已授权的 Agent CLI。具体 CLI 留给实施者根据可用环境选择；不得宣称首期已兼容所有提供方。

暂不包含无人审批的生产部署与合并、公共 Skill 市场、第三方不可信租户托管、原生移动端和多提供方调度优化。Release 保存发布与验证记录，实际部署由团队现有流程执行，后续再接 CI/CD。

失败边界：未执行却报告成功；把运行结束当成交付通过；历史证据随配置改变；同一触发产生重复 PR；取消后在不知情时继续派发；通过导出泄露凭据。界面不能以编造数据掩盖失败或空态。

## 方案选择

方案一为 Python 统一工作平台加独立执行端。服务端管理身份、业务、调度、审计与交付，Runtime 在团队机器上准备仓库并调用 Agent CLI。优点是支持人工与 Agent 并行、靠近已有开发环境；代价是需要执行协议、心跳、租约和断连恢复。用户已明确选择此方案。

方案二为 Python 平台集中管理与执行。所有项目在服务端隔离环境中运行，部署和环境控制更集中，但需要首期建设完整执行基础设施并承担各类项目依赖和凭据运维。因首期成本更高且不如方案一贴合 Multica 的分工，未选。

方案一仍允许未来在云主机部署 Runtime；这不改变服务端不直接执行仓库命令的边界。

## 产品主线

Workpal 管理从意图到交付的协作过程，并把可验证的方法沉淀为团队 Skills。首要用户是项目负责人、执行成员、评审者和工作区管理员；Agent 是被配置、被授权的执行身份。

主线为：收集意图 → 明确范围和验收 → 建立项目上下文 → 分派工作 → 执行并保留证据 → 评审与返工 → 完成和发布反馈 → 沉淀 Skill。

每一步都应回答：当前目标是什么、谁负责、依据是什么、产物在哪里、下一步由谁决定。Chat 可以发起工作，但 Issue 和 Delivery 承担持续记录。

## 页面结构

保留当前主导航，减少迁移成本：Work 下放 Inbox、Issues、Projects；Team 下放 Agents、Squads、Skill Hub、Runtimes、Runs、Workflows 和 Analytics；Chat 管理独立对话；Auto 管理 Autopilots；Settings 管理成员和连接。

Delivery 首先是 Issue 的一级标签和 Inbox 的审核入口，不增加顶层导航。项目上下文放在 Project → Context；环境绑定在 Project → Environments，故障调查在 Chat 的 Environment support 入口与 Project → Investigations，Jira 映射在项目连接设置；发布记录先作为 Project → Releases 扩展，不预先建设独立发布平台。

Issue 详情包含 Overview、Discussion、Deliveries、Activity；右侧保留属性和运行记录。Run 详情分为 Input、Timeline、Artifacts、Usage，明确提示实际失败原因与可用操作。Skill 详情包含 Overview、Content、Versions、Validation、Usage；导入预览展示来源、文件和冲突处理选择。

界面继续使用 Inter、中性表面、紧凑行、克制边框和阴影。390px 窄屏下侧栏变为可关闭面板；状态变化不能只靠颜色；表单、菜单、审核操作均可用键盘完成。保留本地 review notes，界面不加入 prototype、research 或 simulation 标签。

## 对象与状态契约

- Issue 是工作承诺；Run 是一次尝试；Delivery 是一次提交；Review 是对特定提交的决定。四者分别存储和转换。
- Issue 使用稳定 status key，另设 unstarted、started、done、closed 生命周期分类。自定义状态仅归类，不隐含派发或完成行为。
- 默认路径为 Backlog → To do → In progress → In review → Done，另有 Blocked 和 Cancelled。归档是可见性属性，不新增状态。
- Run 首版支持 deferred、queued、dispatched、waiting_local_directory、running、cancel_requested、recovery_required、awaiting_input、completed、failed、cancelled；awaiting_input 是保留检查点后结束当前执行的终态。completed 不自动将 Issue 标为 Done。
- 创建 Run 时固定任务要求、项目资源、Agent 配置、Skill 版本、工作流版本和触发者身份。历史展示不得从当前配置反向重建。
- 同一 Issue 可有多个 Run；较晚返回的 Delivery 默认为候选，不自动覆盖当前提交。切换当前提交必须保留操作者和原因。
- Review 必须引用 delivery_id、version 和当时的验收标准。批准需通过产物与证据检查，并在同一事务中确认该提交仍是当前版本。
- Request changes 保留原评审和提交，下次尝试携带返工原因。修改验收标准后，旧批准不覆盖新要求。
- 人工完成必须记录理由与操作者；审核通过、PR 合并、部署和上线验证分别记录，不能互相替代。

## 四个关键使用场景

### 从讨论形成可验收任务

用户在 Chat 中选择项目，补充目标和限制，进入 Create issue 表单确认标题、范围、验收标准和负责人。保存到 Backlog 不触发执行；显式 Start work 才进入派发校验。验收：来源对话可回看、缺少必要参数时保留草稿、重复提交只创建一次。

### Squad 分工与交付评审

负责人将 Issue 交给 Squad；leader 接收成员职责和项目快照，提出或创建明确子任务。各子任务独立运行、提交，主任务汇总产物。评审者逐条核对证据并批准或退回。验收：成员不会因加入 Squad 就同时启动；子任务执行结束不跳过父任务验收。

### 将经验沉淀为 Skill

从已批准 Delivery 发起 Create skill draft，保留来源和作者，整理适用条件、输入、步骤、输出、停止条件及案例。通过验证后发布不可变版本，Agent 绑定确定版本；新版本展示差异后再升级。验收：历史 Run 可定位当时内容；来源刷新形成候选版本，不覆盖已发布内容。这是相对 Multica 原位刷新的明确扩展。

### 计划任务与异常恢复

创建 Autopilot 时明确时区、触发条件、负责人、执行模式和失败处理。每次触发先记录 admission 结果，再派发；重复 Webhook 复用同一记录。验收：暂停后不再接纳新触发；跳过、派发失败和运行失败分别可见；恢复服务时按显式 misfire 策略处理，默认记录错过而不批量补跑。

## Python 后端设计

采用模块化单体作为目标架构，API、调度 Worker 和执行 Runtime 分离职责。Python 负责业务服务和未来控制进程；第三方 Agent CLI 作为外部执行器，不要求其实现语言为 Python。具体 Web 框架及依赖版本在实施设计中锁定，本轮不安装依赖。

当前 Python 与 SQLite 服务提供本地记录持久化，业务规则仍主要在前端。它不是完整后端：后续需要将权限、状态转换、派发、评审门禁和幂等性移到服务端。不能只将整份前端 JSON 写入数据库就视作完成。

模块边界：identity 管成员与权限；work 管项目与 Issue；collaboration 管评论、Chat 与 Inbox；agents 管 Agent 与 Squad；execution 管 Run、快照和事件；delivery 管产物与评审；skills 管内容和版本；automation 管触发与调度；investigation 管环境、证据、结论与复验；integrations 管外部连接、Jira 缺陷同步与对账；audit 管业务事件和导出。

持久化统一使用 SQLite，涵盖结构化业务记录、追加事件、调度队列、Skills 内容、日志、交付附件与检查点内容；文件内容使用有大小限制的 BLOB 或分块表，元数据与引用在同库保存。不引入 PostgreSQL、Redis 或对象存储，也不预设迁移时间。原型 SQLite 不直接升级为正式产品数据库。工作区身份必须出现在业务查询和写入授权中；客户端提交的 workspace_id 本身不是授权依据。

核心实体包括 Workspace、Membership、Project、ProjectResource、Issue、IssueDependency、Comment、Conversation、Agent、SquadMember、Runtime、Run、RunInputSnapshot、RunEvent、Delivery、Artifact、CriterionEvidence、Review、Skill、SkillVersion、SkillBinding、Autopilot、TriggerDelivery、Notification、AuditEvent。

所有可变主实体带 revision；旧 revision 写入返回冲突，并允许用户比较后重试。创建 Run、触发自动化和外部事件接收使用明确作用域的 idempotency_key。状态修改和待派发事件在同一数据库事务内写入 outbox，Worker 用租约领取；重试按至少一次投递设计，通过幂等约束防止重复业务结果，不承诺外部工具副作用恰好一次。

Runtime 使用独立任务身份，心跳报告能力和可用性。Worker 不在 API 请求进程内直接启动 CLI。取消先记录请求，收到执行端确认后转为 cancelled；断连期间保留未知或等待确认状态。日志支持单调序号和断点续读；敏感内容在写入日志前脱敏。

服务接口按动作表达业务意图，统一由前端与未来 CLI 调用：

| 接口草案 | 服务端约束 |
| --- | --- |
| POST /api/v1/workspaces/{id}/issues | 成员权限、输入校验、幂等创建 |
| POST /api/v1/issues/{id}/transitions | revision、合法状态转换、显式派发规则 |
| POST /api/v1/issues/{id}/runs | 访问权限、Runtime 就绪、输入快照、重复触发处理 |
| POST /api/v1/runs/{id}/cancel | 操作者授权、取消请求和执行确认分离 |
| GET /api/v1/runs/{id}/events?after= | 有界分页、序号续读、工作区隔离 |
| POST /api/v1/issues/{id}/deliveries | 产物引用、验收证据、版本生成 |
| POST /api/v1/deliveries/{id}/reviews | 当前版本、审核权限、证据门禁、并发冲突 |
| POST /api/v1/skills/{id}/versions | 内容快照、来源、哈希、不可变已发布版本 |
| POST /api/v1/autopilots/{id}/trigger | 权限、触发幂等、准入结果和派发记录 |

事件订阅采用服务端推送接口，读取可以回退到分页轮询；具体传输参数在实施计划中确定。所有错误返回稳定 code、可读 message、request_id 和必要的恢复提示。

## 开发交付的端到端行为

以修复上传重试导致重复文件为验收场景。产品负责人创建 Issue，写清重现步骤、预期行为和验收标准；开发者确认范围和方案，选定仓库与基线提交。Start work 先显示计划使用的 Agent、Runtime、Skills、目标仓库及允许的操作，服务端校验后记录输入快照并入队。

Runtime 为 Run 创建专用分支和工作目录，执行修改与测试。Agent 可以提出需要人决定的问题，此时保存等待原因并通知 Inbox；需要继续时产生带新输入快照的后续 Run，保留父子关联。首期不依赖提供方支持实时插话或进程暂停。

等待人决策时，当前进程先停止，保存工作目录检查点，Run 进入终态 awaiting_input；它不占活动运行槽位，也不代表执行成功。检查点包括 base SHA、已有本地提交、tracked diff 与允许保留的未跟踪文件清单及哈希，排除凭据、构建缓存和忽略文件；无法完整保存时显示 checkpoint_incomplete 并禁止自动 Resume。Resume 将人的回答、授权决定和检查点引用写入新快照，在新隔离目录恢复后继续。旧检查点不修改，也不需要先生成 Delivery。原进程尚未确认停止时仍属活动运行，不能 Resume。

开发者或 Agent 提交 Delivery，包含变更摘要、提交 SHA、PR、测试命令、退出码、原始输出引用、验收证据和已知限制。仅有“测试通过”的文本不算测试证据。未经采集的人工报告必须标明由人提交，不能转换成工具执行事件。

评审者在同一页查看要求、diff 引用、证据与限制。退回后再次运行并形成新 Delivery；批准只作用于所审提交，代码托管分支策略仍独立生效，Workpal 的批准不能绕过提供方要求。代码类 Issue 的默认完成策略为当前 Delivery 已批准且对应 PR 的已批准 head 已合并；文档等非代码任务可在批准后完成。合并由有权限的人决定；可通过 Git 服务执行，也可通过 Workpal 的 Merge 操作或 Chat 在展示确定的 PR、head SHA 和检查状态后由人批准执行。平台继续读取并确认合并事实。

PR 增加新提交时，原 Review 保留历史但不再覆盖新 head。Webhook 更新与主动对账均检查仓库、PR、head SHA 及事件身份；延迟事件不得将旧提交批准附着到新提交。Git 服务暂时不可用时显示状态未确认，不推断完成。

项目 Release 关联具体已完成 Issue 和提交，记录目标环境、发布人、部署引用、验证与回退说明。它不自主调用生产部署。首版不建设通用生产部署执行器；如果界面仅支持发布记录，Chat 同样记录，不声称已经部署。

## 派发与工作流规则

首期采用显式派发，避免编辑负责人意外消耗执行资源：保存 Issue、变更状态、绑定 Agent 和添加评论本身不启动 Run。Start work、Retry、Resume、确认的 Chat Send、Autopilot 触发才进入统一派发入口。提及默认通知；用户选择 Run agent 后才派发。这是对 Multica 部分自动触发行为的有意调整。

工作流配置定义状态、允许的转换、责任角色、交付门禁和返工目的地，并支持条件分支、并行子任务、汇合、人工决策、超时和返工；不运行用户输入的任意脚本。新配置只作用于后续 Run，正在审核的 Delivery 继续使用快照规则。Block 记录问题和责任人；解除阻塞不自动执行。

子任务依赖必须在同一工作区，拒绝依赖环。父任务可在依赖完成后进入待决策队列，不因子任务 Run 完成就自动 Done。Squad leader 可以创建分工草案，由人确认后派发；首版同时支持在项目明确授权的 Agent 范围、并发数、子任务数和预算内自动派发，超出边界转人工决策。

## Runtime 协议与恢复

Runtime 是独立 Python 守护进程，运行在团队控制的机器，首期使用出站 HTTPS 领取任务与上报事件，不要求客户端接受公网入站连接。界面实时更新可采用 SSE；轮询和事件读取具有相同授权边界。协议带版本号，能力不兼容时拒绝派发并给出原因。

注册由管理员签发一次性配对凭据，绑定 workspace 与 Runtime 身份。后续使用可撤销的 Runtime 凭据，Run 领取后只获得短期任务令牌，限定对象、动作和有效期。令牌内容不进入模型提示。凭据保存于受限文件或系统凭据设施，具体设施由实施者选择。

Run 具有 lease_owner、lease_epoch、lease_expires_at。领取和续约在事务中校验；只有当前 epoch 可接受状态更新。Runtime 持久化 run_id、进程标识、工作目录、事件游标与待上报事件，重启后先核对实际进程和服务器状态，再决定恢复或报告中断。

服务端超时不意味着远端进程已停止：租约丢失后进入 recovery_required，不立即在第二个 Runtime 重跑。旧执行端必须停止任务；无法确认时由管理员核验并记录处置。受限外部凭据与运行隔离用于降低旧进程继续产生副作用的风险，租约本身不构成操作系统隔离。

事件以 run_id、epoch、sequence 去重；相同键不同内容拒绝并审计。进程结束与事件上传分别确认：日志有缺口时可以记录执行终态，但交付须显示 evidence_incomplete，不能声称完整验证。

Cancel 对尚未领取的任务立即生效；活动任务进入 cancel_requested，执行端终止进程组并确认。断连期间保持取消待确认，阻止替代执行。Retry 始终创建新 Run；基础设施恢复重试有上限，默认最多一次，鉴权、配置或测试失败不自动重试。

同一 Issue 与 Agent 的人工 Start work 首版仅允许一个活动 Run，相同动作键重复 Start 返回已有运行；工作流节点按实例、节点和尝试号单独去重，不套用人工 Start 的复用规则。跨 Issue 并发受 Runtime 槽位和仓库工作目录隔离控制。并行候选 Delivery 的数据模型预留，首期不默认开启同一任务的竞赛执行。

## 仓库与执行边界

首期使用 Runtime 自有仓库缓存与每次运行独立 worktree，固定输入 base SHA，创建 workpal 命名空间的唯一分支。不能修改原型工作目录、用户当前分支或共享缓存中的工作树。后续返工从选定 Delivery 的提交开始，所有基线均可追溯。

在开始执行时明确允许读取、修改、测试、推送任务分支和创建 PR；合并、修改保护规则与部署不在 Agent 默认权限内。需要额外操作时记录 approval_required，由有权限的人作出决定。Skill 中的指令不能提升授权。

初期只接受团队可信仓库和可信提供方，Runtime 运行于专用系统用户或专用容器，限制可访问目录与凭据。worktree 只提供 Git 工作隔离，不视为安全沙箱。不将公共不可信仓库执行作为首期能力。

PR 创建使用 run 与仓库的持久 operation key；外部调用超时后先按分支和仓库对账，不盲目重建。推送使用预期分支状态检查，禁止强推他人分支。测试结果记录命令、工作目录、提交、退出码与时间，禁止将旧提交测试用于新提交的批准。

GitHub 与 Azure Repos 写操作通过 Runtime 的受控操作代理完成，Agent CLI 不持有代码托管写凭据。CLI 可在隔离目录本地编辑和提交，再请求 push_branch 或 create_pr；代理核验当前任务授权、仓库、允许分支、预期提交与操作键后执行。代理以独立系统身份保存凭据，任务进程不能读其文件、环境或进程接口。任务侧禁止继承用户 gh 配置、SSH agent 和通用 Git 凭据。普通执行 Agent 只允许上述动作，不提供任意代码托管 API 转发。合并使用独立的人批准操作：服务端核验当前用户权限、PR head、检查结果与一次性授权，再由受控代理执行，不能通过编码 Run 的任务令牌调用；不开放保护规则修改和任意部署操作。提供方自身的模型认证单独配置，不共享代码托管写权限。此代理属于首版的必要执行边界。

## 权限与数据管理

首期提供管理员创建的本地团队账号、服务端会话和 owner、admin、member 三种角色，不开放公共注册。密码使用成熟哈希库，框架和认证依赖由实施者在计划阶段核验选择，禁止自制密码学。

工作区成员默认可读普通业务记录；受限环境的调查、证据与派生回答按环境数据权限收窄；member 可创建和编辑任务，只有获准使用 Agent 与 Runtime 的成员可执行；项目 reviewer 可批准或退回，Agent 不能批准自己的产物。owner 和 admin 管成员、连接、Runtime 和配额。批准和执行时均实时检查权限，不能只信任创建时的权限快照。

授权快照用于解释历史，当前授权用于允许下一次副作用。撤销成员或 Runtime 凭据后停止新任务和新令牌签发，活动执行进入取消流程。执行中无法立即收回已经发给外部 CLI 的权限时，界面保留这一未确认状态。

产物内容及元数据首期都存入 SQLite，按 workspace、哈希、大小与所有者管理，通过授权下载接口读取。上传分块暂存，最终校验哈希后原子发布引用，失败上传不可成为审核证据；不依赖长期外部文件目录。建议默认单产物 25 MiB、单次运行产物总计 250 MiB，超限记录明确错误。原始执行日志保留 90 天；被 Delivery 引用的证据随 Delivery 保留，不能被日志清理破坏。清理和导出均有审计记录。

备份使用 SQLite 在线备份接口获得一致性快照，包含全部业务记录和产物内容，校验哈希及恢复后的引用；不得在活跃 WAL 写入期间只复制主数据库文件。Runtime 本地待同步日志单独备份或恢复，不把中央库备份当成未上传执行数据的备份。离线 HTML 导出只包含用户有权导出的选定记录，默认排除执行原始日志和全部凭据；用户文本转义。离线文件不能实施服务器权限，也不支持自动回写合并。

## 独立 Chat 的完整首版行为

对话绑定项目、参与 Agent 和可选 Squad，支持创建、重命名、置顶、归档、草稿与消息历史。Send 显式触发真实 Run；每条消息保留原文、附件和上下文快照。流式响应来自实际 Runtime 事件，断线重连按序号续读，不制造模型回复。用户可停止执行、补充输入并继续，错误和等待决策状态可见。

同一对话首版串行执行；运行时的新消息进入可撤回的待发送队列，不冒充已被 Agent 接收。跨对话可并发。转为 Issue 前展示目标、验收标准和历史范围，确认后创建链接与不可变来源快照。对话可产生产物，但不需要虚构 Issue；需要正式验收的结果转入 Issue 的 Delivery 流程。Chat 与 Issue 共用 Runtime、权限、Skill 和产物服务。

## Chat 作为完整操作入口

这是首版核心能力：用户用一句话描述目标，Workpal Agent 识别意图、读取相关上下文、补齐可推导参数、组织操作并实际完成；用户不必知道页面位置、对象 ID、接口或逐步点击顺序。例如“给上传模块建一个修复项目，拆出开发和测试任务，交给对应 Agent，完成后通知我评审”，可以形成项目、Issue、分派、运行和通知的连续操作。

覆盖范围是 Workpal 中当前用户能通过界面完成的全部业务操作，包括工作区切换、项目与资源管理、Issue 与评论、分工、Agent 和 Squad 配置、Skill 内容与绑定、工作流、Run 控制、自动化、连接设置、Inbox、分析查询、交付评审、导出、环境证据调查、原因分析、Jira 缺陷与关联修复和获准的 PR 合并。首版不接受“只有部分命令支持 Chat”的功能交付；如某项界面功能需要用户完成外部 OAuth 或输入秘密，Chat 引导进入对应安全控件并在完成后继续，不要求用户在消息里粘贴凭据。

这里的“全部”以 Workpal 业务操作与已接入工具为边界，不自动授予操作用户整台电脑、任意网站或未连接服务的能力。外部手工动作只有形成明确连接和受控操作后才可调用；对不可用能力如实说明并保留待办，不生成虚假完成记录。

### 共用操作目录

前端按钮与 Chat 工具调用共用服务端 Action Registry。每项操作声明稳定 action_id、输入与输出 schema、读写性质、资源作用域、授权规则、前置条件、幂等性、确认策略、可撤销方式和审计字段。界面不保留 Chat 无法访问的独立业务写入路径；Agent 不直接写数据库，不通过模拟鼠标点击实现常规操作。

工具调用身份绑定提出请求的人，使用当前工作区和当前权限。Agent 不继承管理员或 Runtime 所有者权限。每步重新校验授权与 revision，权限中途撤销时停止后续写入。用户贴入的文档、仓库和 Skill 内容是任务材料，不能修改操作权限或发起与用户目标无关的动作。

Action Registry 是唯一业务行为目录；工具描述由它生成，模型输出必须经过 schema 校验。读取可按权限自动进行；缺少名称可以从当前项目推导，遇到同名仓库、不同目标分支或相互冲突的范围才提出一个聚焦问题。不能把模型推测当作用户已经授权扩大删除范围或增加外部接收人。

### 从一句话到完成

ChatRequest 保存用户原话、工作区、目标对象与请求 ID。ActionPlan 保存有依赖的操作步骤、参数、读到的版本及需要用户决定的节点；ActionExecution 为每步保留结果 ID、状态、错误和副作用引用。三者都在 SQLite 中持久化，页面关闭或服务重启不会让已经执行的步骤丢失。

低风险、可恢复且目标明确的操作直接执行，不要求用户逐个确认。例如创建项目、拆任务、修改描述、调整负责人和生成报告。长流程展示简短计划和进度，用户可以补充要求或停止；不是要求先手工填写所有页面再让 Agent 点击保存。

删除数据、权限授予、秘密轮换、PR 合并及任何未来部署操作先形成具体可审核请求。确认卡显示对象、数量、目标、提交版本和不可逆影响，允许一次批准同一目标下的一组明确动作，不做逐步弹窗。确认绑定参数摘要、资源 revision、用户与有效期；计划变化、PR head 改变或目标增加后原确认失效。用户一句“帮我处理所有事情”不构成无限期授权。

不把人工评审改成 Agent 自我批准。Chat 可以整理证据、指出缺口并准备评审决定；最终批准由有权限的用户在消息或确认卡中对具体 Delivery 作出，记录用户为决策者、Agent 为执行代理。对用户明确指定且对象无歧义的批准指令可以作为确认，但仍需满足证据和版本门禁。

需要外部认证时状态为 waiting_user_auth，授权完成后重验计划并继续。需要决策时为 waiting_confirmation 或 waiting_input。自动执行只在所有前置条件满足后恢复，不靠页面的按钮状态判断授权。

### 协调与执行槽位

ActionPlan 的持久化协调器运行在 Python 服务端 Worker，不占用 Agent Runtime 槽位。Chat Agent 只在理解目标、生成计划或处理结果时启动短轮次 Run；派发开发 Run 或工作流后即保存计划并结束当前协调轮次，释放槽位，不持有进程等待子任务或人工确认。

服务端依据已持久化业务事件和待执行步骤恢复计划，需要模型判断时才启动新的协调 Run，并引用原 ChatRequest、ActionPlan 和已确认结果。Runtime 仅一槽时，协调与开发依序执行，不发生协调器占槽等待自己的子任务。子 Run 的输出只是数据，后续动作仍由当前用户授权及操作目录约束。

停止、确认、补充输入和撤回消息是控制操作，走独立接口，不被同一对话普通消息队列阻挡。对话串行指同一会话不同时开展两个未协调的用户目标，不限制必要子任务按计划并行。Stop 直接标记计划取消并通知子执行，不能等待 Chat Agent 先读到消息。验收增加单槽派发后完成、等待确认不占槽、服务重启恢复计划和停止请求及时生效。

### 失败和控制

一个请求可能包含多个已提交事务，不承诺跨 Git 服务和 SQLite 的原子回滚。失败时显示已完成、未执行、失败和需要处理的步骤，并链接真实对象。补偿只对目录中声明可恢复的动作执行，不能删除用户随后修改的记录、撤销他人权限或抹去已推送提交。

每步使用 request_id 与 step_id 范围内的幂等键；外部调用超时先对账再决定重试。用户重发同一句话不自动判成重复，应结合会话中现有请求提示继续或另建；重试按钮则明确复用现有请求和未完成步骤。Stop 停止未开始的步骤，对运行中的可取消动作发送请求，保留已完成结果并显示未确认的远端状态。

执行结束以实际操作返回结果总结，给出对象链接、待决定事项和失败原因。Agent 的自然语言“已完成”不能驱动任务、评审或发布状态；状态以业务服务确认的事实为准。

### 覆盖与验收

建立 UI action_id 与 Chat tool 的覆盖表，首版所有可操作业务按钮都必须映射到已授权工具或明确的安全用户交互步骤，发现缺口就视为功能未完成。视觉偏好等纯客户端设置也提供受限客户端动作，不让 Agent 执行任意 JavaScript；服务端不能把本地偏好同步当成业务完成。

验收包括：一句话跨模块建立项目并启动开发；查询后批量调整任务；创建并启用定时工作流；将交付沉淀并绑定 Skill；准备并执行人的明确评审决定；指定 PR 合并的确认与 head 变化失效；重名对象澄清；权限拒绝；用户取消；服务重启恢复；部分外部失败后对账；所有创建结果有真实对象且无重复写入。用确定性的模型输出替身验证协议与权限，再在授权的真实提供方上验证自然语言端到端，不把匹配少量固定关键词视作完成。

## 可配置工作流的完整首版行为

WorkflowVersion 是不可变图，节点类型包含人工确认、Agent 任务、条件、并行分支、汇合和交付评审。WorkflowInstance 固定定义版本、业务主体要求及授权，主体为 Issue 或 AutomationRun，NodeAttempt 保存每次尝试、输入、状态和输出。仅编辑草稿，发布前验证起点终点、可达性、依赖、角色和条件字段。

条件用服务端允许的字段和操作符表达，不执行任意代码。并行汇合默认等待所有必需分支成功，失败进入明确的重试、返工或人工处理节点；可选分支不阻塞汇合。返工循环必须设最大次数，达到上限转人工。发布时拒绝无界循环和无法完成的汇合。

工作流 Agent 节点默认共享所属业务主体，但各自拥有独立输入和产物空间；只有显式“创建子任务”节点才创建子 Issue。派发幂等键包含 workflow_instance_id、node_id、attempt_no。相同 Agent 的并行节点在容量不足时排队，不复用彼此的 Run；不同工作目录隔离，汇合节点只读取明确选定的产物，不自动合并代码或覆盖文件。

节点状态为 pending、ready、running、waiting_input、succeeded、failed、cancelled、skipped；节点 Run 与节点本身独立，Run 正常结束不自动通过证据门禁。取消实例阻止后续派发并向活动 Run 请求取消；恢复实例从已持久化节点状态继续，不重放已经完成的外部写入。工作流权限不能超出触发人的当前授权。

## 自动化与 Skills 的完整首版行为

Autopilot 支持 schedule、webhook 和 manual，支持 create_issue 与 run_only。配置时必须选择时区、负责人、输入模板、工作流或任务动作、并发上限和输出归属。run_only 产物关联 AutomationRun，可从历史直接审阅，不凭空生成 Issue。run_only 可启动完整工作流：WorkflowInstance.subject_type=automation_run；输入要求来自本次自动化快照。Delivery 使用 subject_type 与 subject_id 关联 Issue 或 AutomationRun，两种主体复用版本、证据和 Review 门禁；审核通知都进入 Inbox。自动化审核通过只完成 AutomationRun 或进入下一节点，不执行 Issue 状态转换。接口补充 POST /api/v1/automation-runs/{id}/deliveries，读取与评审继续使用 delivery_id。服务端持续调度，关闭浏览器不影响执行。

触发、准入、派发和执行分别留档；以自动化与计划时刻或外部事件 ID 做幂等，已在运行时默认记录 skipped，暂停后拒绝新准入但不隐式取消已有任务。错过时间默认不补跑，允许配置有次数上限的补跑策略。人工重放创建新的触发记录并关联原记录，不能删除失败历史。

Skill 支持创建、文件和来源导入、编辑草稿、内容差异、验证案例、版本发布、绑定、升级、停用和废弃。验证记录明确输入、预期、实际产物、执行环境与评审；自动检查与人评审分别存储。发布版本不可变，来源刷新形成草稿，绑定默认固定版本，升级需显式选择。只导入和审阅文件，不执行来源页面的安装命令。

## 真实环境故障调查与 Jira 修复闭环

### 目标与来源边界

用户可以直接在 Chat 描述 SIT、UAT、PRD 等环境的问题，由 Agent 调查实际证据、解释原因、给出方案，并按用户意图创建 Jira 缺陷和启动修复。这是首版必备能力。用户已确认日志、监控和发布记录的数据源暂未确定，因此不绑定厂商，也不把连接配置占位或预设对话当成真实接入。

Multica 的[环境文档](../../../../multica/server/internal/service/builtin_skills/multica-platform/references/environments.md)描述的主要是本地开发服务及其生命周期。Workpal 的远程环境调查、证据关联与 Jira 修复闭环属于扩展设计。现有 src/environment-chat.js 只是 DEV、UAT、PRD 的作者编写示例与本地队列，不访问环境；新产品必须新增 SIT，并支持自定义环境名称。

### 从问题描述开始

用户示例：“UAT 今天上传重试后出现两条记录，帮我查原因；如果需要改代码，帮我提 Jira 缺陷并开始修复。”

Chat 从当前项目、用户文字及已有环境绑定确定服务和环境，自动读取已授权的有限范围证据；只有环境、时间窗口或目标服务存在影响结论的歧义时才追问。未提供时间时可先查询项目默认的最近 30 分钟，并明确展示实际查询窗口、时区和数据覆盖范围；不能用这个默认窗口代替用户明确说的时间。排查范围不足时扩大查询须记录原因并遵守预算。

“这是什么原因”授权读取与分析，不自动创建 Jira 或启动修复；“提缺陷并修复”则可形成完整 ActionPlan，已有信息和权限充分时无需每一步再确认。用户也可以在答案后选择 Create Jira defect、Start fix 或 Continue investigation。所有操作同时出现在界面和 Action Registry。

一次完整交付依次为：问题与环境确认、证据收集、原因分析、处理方案、Jira 缺陷关联、Workpal 修复任务、隔离分支修改与测试、PR 与人工评审、目标环境复验。故障可能来自代码、配置、数据、依赖或容量，不能为了启动编码而把所有问题都断言成代码缺陷。

### 环境与数据源

Environment 按 workspace 与 project 隔离，保存名称、环境级别、服务清单、负责人、时区、仓库映射、部署记录来源、允许访问的数据源与查询授权。SIT、UAT、PRD 是默认名称，名称本身不授予权限；不能因同属一个项目就自动访问所有环境。

EnvironmentDataSource 声明 source_id、adapter_type、network_zone、credential_ref、允许的服务与资源、只读能力、字段映射、查询预算和最近连接验证结果。能力目录包括 search_logs、query_metrics、get_trace、list_deployments、get_deployed_revision 与 read_config_diff；数据源只注册真正支持的能力。权限不足、未连接、无数据、采样截断和数据延迟分别反馈。

首版提供真实日志文件与错误信息上传，以及可配置的只读 HTTP 查询适配器。HTTP 适配器由管理员绑定具体可信服务、固定端点、参数 schema、响应字段和脱敏策略；Agent 只能传受限查询参数，不能提交任意 URL、脚本、SQL 或可写请求。端点认证、请求方法和是否只读按实际 API 契约配置，不能简单认为所有 GET 安全或所有 POST 都是写入。

私网数据通过获准的 Runtime 数据采集代理查询，公网或平台可达数据由服务端连接器查询；两者输出统一证据结构。允许访问的主机、端口、资源和方法固定，重定向不得逃逸授权范围。共享连接仅提供传输凭据，Agent 可读范围仍取用户与环境授权的交集，不能借连接所有者的更大权限扩大读取。

用户确定现有系统后选择或实现厂商适配器；不在此时宣称已支持全部监控产品。测试桩用于协议验收，真实部署必须至少接入选定环境的一项真实证据源，并完成可追溯调查后才能宣布实时排查已可用。手工上传的真实材料也可分析，但结论须说明输入来自用户且可能不完整。

### 证据与回答质量

每份 EvidenceSnapshot 保存环境与服务、source_id、脱敏查询、查询时间范围、实际事件时间、采集时间、时区、事件或请求 ID、部署标识与可用的 commit SHA、截取范围、内容哈希和原始位置链接。查询日志、指标、链路与发布信息优先按时间、request/trace ID、服务版本关联；不能把当前 main 代码当成环境正在运行的代码。

Agent 将问题分为 observed facts、hypotheses、verification 和 recommendations。每条主要结论引用可授权查看的证据，指出支持证据、反证、缺口及下一验证动作。不生成没有测量依据的概率数字；时间相邻、近期发布或报错频率同时上升，只能构成关联线索。调查允许得到“当前证据不足以确定原因”的有用答案。

Finding 状态包括 hypothesis、supported、confirmed、rejected；升级为 confirmed 必须引用能区分关键替代解释的验证记录，例如对照重现、运行版本与具体故障路径的证据链，或经授权实施后的对照观测。状态变更保留作者与依据，不能仅因模型重复同一结论升级。不能对某条上传日志进行分析后声称已读取整个环境。

默认答案先给当前判断与影响范围，再给证据、待验证点、临时缓解方案、长期修复方案及验收方式。临时缓解和代码修复分别列出前提、风险、验证与回退条件。已经实施、仅建议、无法执行的动作严格区分。

### Jira 建单与同步

Jira 操作使用当前用户授权的连接；若团队使用共享服务身份，必须另外验证发起人的 Jira 项目访问与操作授权，不能直接以服务身份的全局权限代行。Agent 的审计记录同时保留发起人和外部实际执行身份。JiraConnection 记录实例类型、基础地址、用户授权连接和可访问项目；JiraProjectMapping 将 Workpal 项目映射到选定 Jira 项目、缺陷类型、环境字段、组件和状态映射。Jira Cloud 与 Data Center 使用独立适配契约，不假设 API、用户标识、富文本和认证完全相同。用户尚未指定实例类型；实施接入前必须确认目标实例及版本，未验证的类型显示不可用，不借此推迟 Jira 建单这一首版能力。

首次配置读取真实项目和可创建问题类型，再查询目标类型的必填字段与允许值。不要硬编码 Bug 名称、缺陷类型 ID、优先级或状态 ID。能从项目映射和问题证据推导的字段自动填写，只对缺少的必填信息追问。用户可以预设默认 Jira 项目和分派规则，之后一句话复用。

缺陷内容包括症状、环境与服务、影响、发生时间、重现步骤或尚未重现的说明、期望与实际结果、已知部署版本、证据摘要、原因的验证状态、建议修复和验收标准。原始日志默认不随单发送；只发送通过环境导出策略允许的脱敏摘要，详细证据用受限 Workpal 链接引用。目标 Jira 受众不满足数据策略时，停止外发并保留本地草稿，不将 PRD 信息扩散给更大人群。

用户已要求建单且目标明确时直接创建。ExternalMutation 先在 SQLite 保存 operation_id、目标实例与项目、请求摘要和状态，再调用 Jira。只有收到并核验真实 issue ID、key 和 URL 才显示 Created；超时为 unknown，不盲目重复创建。相同操作先用外部关联标记及查询核对；Jira 不提供通用可靠幂等时，无法唯一确认就转人工对账，不能承诺外部创建恰好一次。

先搜索相关未解决缺陷，精确已有 ExternalIssueLink 可直接复用；相似内容只作为候选，不能仅凭语义相似自动合并两次故障。创建成功后按外部 issue ID 幂等建立本地修复 Issue，存储 Investigation、Jira、Workpal Issue、Run、Delivery、PR 的双向引用。

Jira 创建失败时调查结果和建单草稿保留，默认暂停依赖建单的修复派发；用户可显式选择先本地修复再同步。Jira 成功而本地写入或派发失败时按已有外部 ID 恢复，不重新建单。页面分别显示建单、关联、派发、修复、复验各步结果。

Jira 的项目字段和外部状态以 Jira 为准，Workpal 的执行、证据和评审以 Workpal 为准。进度、PR 与处理结论按配置追加评论或受限字段同步；变更 Jira 状态前读取当前可用转换并验证权限，不直接写一个想象的 Done。外部取消、重开或字段冲突保留双方事实并通知负责人；外部取消会暂停未开始的修复步骤，活动 Run 按已配置的取消规则处理。有限轮询为必要后备，Webhook 只是刷新信号。

接口依据为 [Jira Cloud Issues REST API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/)，其中包含建单、创建字段元数据、读取和状态转换接口。Workpal 的字段映射、幂等对账、数据外发和修复关联规则是本设计约定，实际适配按目标 Jira 部署验证。

### 从原因到实际修复

修复 Issue 固定 Investigation 的环境、服务、受影响发布版本、已知事实与假设、重现和验收标准。仓库与目标分支从项目及发布映射获得；发现多个可能仓库或无法确定热修复基线时先提出聚焦问题，不能默认修改 main 就代表修复 PRD。

Agent 在隔离开发目录基于选定版本重现故障，尽量先建立能够失败的回归测试，再修复、验证并提交 GitHub 或 Azure Repos PR。无法重现时记录验证限制和需要补充的数据，不伪造“修复前失败、修复后通过”。生产数据不默认复制到开发目录或外部模型。

“开始修复”授权代码层的受控开发流程，不自动执行生产数据库写入、配置变更、服务重启或部署。首版诊断数据源保持只读；非代码问题可建缺陷或整改任务并给出人工操作方案，未接入的环境写操作不能标为已执行。

Investigation、修复 Issue、Jira issue 和环境恢复状态独立。Investigation 状态为 investigating、waiting_evidence、recommendation_ready、monitoring、resolved，取消单独留档；Finding 的可信状态另行管理。PR 合并可完成代码 Issue，但调查仍需记录目标环境实际部署版本和复验结果，必要时由有环境权限的人确认恢复。

复验保存观察窗口、目标指标或用户可见行为、发布标识和证据；没有原故障或仅一个成功请求不能自动证明恢复。满足预定复验标准并由指定负责人确认后才能 resolved；允许恢复已确认而根因仍未知，并明确保留未确认 Finding。Jira 关闭默认需要完成对应修复与复验门禁，不能仅凭 PR merged 自动关闭。故障再次出现可重开 Investigation 并关联原缺陷，保留之前版本和恢复记录。

### 数据对象与权限

新增 Environment、EnvironmentService、EnvironmentDataSource、Investigation、InvestigationEvent、EvidenceSnapshot、Finding、VerificationRecord、JiraProjectMapping、ExternalIssueLink、ExternalMutation。调查可先关联 Conversation 而没有 Issue；正式修复时才绑定 Issue。调查与修复 Run 的输入快照包含 environment_id、service_id、部署版本、证据版本与查询范围，后续改环境绑定或数据源配置不改写历史依据。相关记录与有界证据内容统一进入 SQLite，外部日志平台仍是完整日志的来源，Workpal 不镜像全部遥测。

普通工作区可见性不适用于受限环境证据。调查、回答、派生报告、Jira 外发、搜索索引和导出都继承环境与来源数据的限制；链接不能绕过授权。日志、错误消息、工具输出和 Jira 内容均是不可信任务数据，其中包含的指令不能更改任务目标、导出目的地或操作权限。查询结果在进入模型上下文和持久化前做脱敏，必要时仅提取允许的字段；数据策略不允许发送到所选模型时拒绝发送并给出可用处理路径。引用保留来源与可验证哈希，脱敏不伪造原始内容。

受限调查派生的修复 Issue、子任务、评论、Run 输入与日志、Delivery、附件及导出默认继承原环境的访问限制，不因进入普通任务流程而变成全工作区可读。服务端按当前访问策略组装 Runtime 上下文；没有该环境权限的 Agent 使用者不能通过分派、报告或对象引用取得原始材料。多来源派生对象采用最严格的适用限制；撤销环境访问后，相关引用和派生视图同步收窄。

面向更广泛受众的 Jira 内容、代码补丁、测试数据、提交消息和 PR 必须使用单独的发布载荷。发布前按环境外发策略检查，使用合成的最小复现数据代替生产原始记录，不能把用户数据、敏感请求标识或日志直接写进回归测试。仅掩码字符串不自动解除限制；降低可见性限制须由具备环境数据发布权限的人批准具体内容与目的地，并保留来源及批准记录。未经允许则保留受限草稿，禁止推送；外发批准不改变原始调查与证据的访问权限。验收增加“受限 PRD 调查转普通修复并尝试外发 PR”的泄露阻断用例。

默认查询窗口 30 分钟，单次最多 1000 条或 2 MiB、30 秒超时，一次调查默认最多 10 次查询；均可由管理员调整，截断和预算耗尽必须显式记录。支持分页与细化查询，不默认抓取整个环境。已引用证据随调查和交付保留，环境保留策略要求删除时清理引用内容并标记不可再访问，不能保留可绕过删除的摘要副本。

操作目录至少包含 environment.list、investigation.start、evidence.query、evidence.upload、investigation.explain、jira.search_defects、jira.create_defect、jira.link_existing、repair.start、verification.record 与 investigation.resolve。接口复用前述 ActionPlan、授权、幂等、等待与取消机制；读工具失败不会被解释成没有故障。

### 首版验收

1. 在 SIT、UAT、PRD 与自定义环境中，描述问题后能绑定正确服务、查询授权数据或接收真实上传，答案引用真实证据，未知根因明确显示未知。
2. 在受控测试环境制造已知故障，关联部署版本与日志，给出正确原因或可验证假设及方案；移除关键证据后不得继续声称已确认。
3. 一句话“建 Jira 缺陷并修复”真实生成缺陷、建立本地关联、启动隔离修复、记录回归测试并创建 PR，所有链接可验证。
4. 必填自定义字段、无创建权限、认证过期、创建超时后重试、Jira 已存在、本地保存失败与派发失败均有可恢复状态，无盲目重复建单。
5. 不能访问另一环境、不能将敏感日志外发，未接入数据源不能返回伪造诊断；Jira 受众不满足策略时保留草稿。
6. 代码已合并但尚未部署、部署后复验失败、缺陷重开分别保持真实状态；只有目标环境满足复验条件才记录恢复。
7. 工具协议、错误路径与权限可先用测试桩验证；真实链路最终需要选定的证据源和 Jira 实例参与验收。来源未确定不阻止设计与接口实现，也不能用测试桩代替实时接入验收。

## SQLite 部署与一致性

初期采用单主机部署，一个 Python API 服务和一个调度 Worker，访问本机磁盘上的同一 SQLite 数据库；Runtime 只通过 API 通信，不共享数据库文件。启用 WAL、每连接外键校验和有界 busy timeout。部署不把数据库置于网络共享文件系统，也不运行多个可写服务器副本。

数据库事务保持短小：网络请求、Agent 执行、哈希计算和大文件读取在事务外完成；任务领取使用 BEGIN IMMEDIATE 加条件更新及受影响行数判断，不假设 SQLite 提供行级 SELECT FOR UPDATE 或 SKIP LOCKED。revision、租约 epoch、幂等键与唯一索引共同防止重复业务动作。锁竞争按有限退避重试，耗尽后返回可重试错误；不静默丢弃写入。

事件和 BLOB 分块有界批量写入，避免长日志和附件阻塞审核或心跳。测试必须覆盖两个连接同时领取、并发审核、写锁超时、磁盘满、进程中断和备份恢复；容量不足返回明确失败，不接受无法持久化的成功状态。

Runtime 以自身 SQLite 保存租约恢复信息和待上报事件，中央库保存已确认的平台事实。Git checkout、进程运行目录、工具依赖与临时文件仍必须落在 Runtime 文件系统，它们是执行环境，不构成另一套业务存储。密钥仍保存在受限凭据设施，数据库仅存引用；“数据统一 SQLite”不要求把明文密钥放进数据库。

SQLite 依据：[WAL 部署约束](https://sqlite.org/wal.html)与[在线备份接口](https://sqlite.org/backup.html)。

## Azure DevOps 仓库接入

ADO Repo 在本文指 Azure Repos Git。首期默认目标为 Azure DevOps Services；Azure DevOps Server 的内网地址、API 版本与认证兼容作为后续独立适配，不把云服务支持宣称为任意 Server 版本兼容。TFVC、Azure Boards 双向同步和创建 Azure Pipelines 不包含在本次 Repo 范围；可读取已有 PR 策略和检查结果。

仓库连接记录 provider、base_url、organization、project_id、repository_id、clone_url 与默认分支。GitHub 使用其仓库稳定 ID；Azure Repos 的身份由组织、项目和仓库稳定 ID 共同确定，不只以仓库名称去重。界面显示 Organization、Project、Repository，并保留原始 PR 链接。

统一代码托管接口包括验证访问、读取仓库与引用、读取提交和 diff、推送受限任务分支、创建或查找 PR、获取 PR head 与合并事实、读取评审和检查状态、执行人批准且绑定 head 的 PR 合并、接收事件及主动对账。GitHub 与 Azure Repos 分别适配，不将 Azure Repos PR 编号当成全局唯一键。PR 主键包含连接、仓库和提供方 PR ID。

Azure Repos 的 PR 创建与读取使用官方 Git REST API；状态变化可由 Service Hooks 通知，再主动读取权威状态。Workpal 统一显示 open、merged、closed，同时保存原始状态；abandoned 不等于 merged，completed 必须同时核验实际合并提交与已批准 source head。未能取得策略评估或检查结果时显示 unknown，不默认为通过。

首期支持用户配置的组织范围、最小权限、短期 Azure DevOps PAT，受控代理保存凭据引用并限制实际动作；凭据轮换不改写历史。PAT 不进入提示、日志、clone URL 或导出文件，也不传给 Agent CLI。企业禁用 PAT 时连接明确不可用，不能绕过其认证策略；Entra 认证作为后续连接方式。建立连接只验证访问，不自动开启自动完成、调整分支策略或执行合并。

Service Hooks 接收端独立认证并校验所属连接，不套用 GitHub 的签名协议。通知只作刷新信号，确认状态依赖有授权的 REST 查询。重复、乱序、缺失事件分别通过事件键、head 校验和周期对账处理；本地服务不能接收外网回调时使用有界轮询，仍支持完整 PR 生命周期。

首版分别在 GitHub 与 Azure Repos 验证：仓库连接、独立分支修改、测试证据、PR 创建去重、退回新提交使旧批准失效、合并确认、凭据失效与恢复、事件不可达时的轮询。提供方适配必须使用各自测试桩覆盖，真实验收在后续获得相应账号与测试仓库授权后进行。

认证方式的正式部署选择遵循组织策略；Microsoft 优先推荐 Entra 身份，PAT 方案仅用于允许该方式的首期接入，见[认证说明](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops)。

来源：[Azure Repos PR REST API](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests?view=azure-devops-rest-7.1)；[Service Hook 事件](https://learn.microsoft.com/en-us/azure/devops/service-hooks/events?view=azure-devops)。上述接口与事件能力来自官方文档；Workpal 的统一接口、权限边界和首期范围是本设计决定。

## Access and update normalization

`project_access.go`, `project_member.go:48-378`, `project_delete_permissions.go`: private visibility requires project membership, even for workspace owners/admins. Agent access derives from human principals/owner and fails closed without attribution. Any visible caller reaching UpdateProject may edit ordinary fields; it is not an admin-only operation. Access changes require a human and workspace owner/admin or private access manager. Manager ordering is member lead, member creator, earliest membership, self-adder tie-break then user UUID (`project_member.sql:GetProjectAccessManager`). Workspace-visible projects have no manager; only owner/admin manages their access.

`project.go:613-766`, `project.sql:UpdateProject`: omitted fields preserve values. Explicit null title/status/priority preserves values; empty title is accepted without trim. Status and priority empty strings are invalid; enums are planned,in_progress,paused,completed,cancelled and urgent,high,medium,low,none. Invalid enum message is `invalid status "active"; valid values: planned, in_progress, paused, completed, cancelled` (priority analogous). Description/icon/lead_type/lead_id presence flags distinguish omitted from null: null clears, empty text persists, empty lead UUID returns 400 `invalid lead_id`. Dates omitted preserve; null/empty clear; other values require calendar YYYY-MM-DD. No ordering requirement between dates. Unknown fields are ignored, including workflow_id, creator and archive fields; no workflow transition is performed. JSON type mismatches fail 400 invalid request body; JSON null is an empty update. Even empty update writes updated_at.

Visibility null preserves; empty string is invalid when different from current visibility. Switching private seeds caller and eligible member lead plus supplied IDs; switching public retains stored membership. member_ids is additive, never a replacement. On public target every supplied ID must already be a project member or 400 `member_ids only adds members to a private project`. Private lead changes require access manager; newly selected member lead is added. UUIDs deduplicate. Outside-workspace IDs reject with 400 `user <uuid> is not a member of this workspace`. Invalid lead_type DB CHECK maps to 400 `project update rejected: a field value failed a database constraint`; other write errors return 500 failed to update project.

Without access changes UpdateProject is one SQL statement (ID-only after scoped lookup). With changes, transaction order is UpdateProject, AddProjectMembers, verify all requested IDs exist, UpdateProjectVisibility if needed, touch search index, commit. Any error rolls back all writes; begin/add/list/search/visibility/commit errors retain the exact messages in `project_member.go:302-401`. Success publishes members_changed if addIDs nonempty, then updated; duplicate additions can still publish. PUT response stats are read after commit.

## Membership fixtures and failures

`project_member.go:414-613`, `project_member.sql`: GET returns `{members:[],total:0,manager_id:null}` for empty public project. Each member has project_id,user_id,name,email,avatar_url (nullable),added_by (nullable),created_at. workspace_role is omitted on these routes. Order is created_at ASC,user_id ASC. Private manager_id is selected as above. POST user_ids must contain at least one valid UUID; omitted/null/empty returns 400 user_ids is required. Human actor and access manager required; agents return 403 agents cannot change project access. POST is atomic add/validate/search touch/commit, returns 200 by calling GET after commit, with full current list rather than inserted rows. Consequently a response read failure can occur after durable commit/event.

DELETE requires same actor/manager checks; no ordinary self-removal exception. Current member lead cannot be removed: 409 change the project lead before removing the current lead. Unknown member returns 404 project member not found. Successful delete persists before search touch; touch failure logs warning and still publishes/returns 204. There is no transaction combining deletion and search touch. Removing self is allowed for an authorized manager who is not current lead, including last member; do not invent a last-member guard. Exact denial messages: `only workspace admins and the member who manages this project's access can add members`, `... can remove project members`, `... can change project visibility`, `... can change the project lead`.

## Deletion and SQLite translation

`project.go:768-855`, `project_delete_permissions.go`: visibility gate runs before deletion permission. Human owner/admin, exact creator actor, or human owner of creating agent in same workspace may delete. Unknown creators confer no rights; mutable lead confers none. Unbound machine credential is 403 project deletion requires a human or a bound agent identity; bound agent must match creator and does not inherit token user's admin role. Otherwise 403 project deletion is restricted to its creator, the creating agent's owner, and workspace owners or admins.

Single transaction: lock scoped project FOR UPDATE; clear chat_session project context; delete project-scoped issue views; delete project_member; delete project_subscriber; delete scoped project; commit. Rollback on each failure; companion catalog preserves exact handler errors. Lock missing yields 404. Chat creation uses FOR KEY SHARE, preventing new dangling soft references after sweep (`project.sql:LockProjectForChatSessionCreate`, chat-session query ClearChatSessionProjectByProject).

# Onboarding completion and cloud waitlist

Source-derived contract; fixtures are illustrative fixed-clock rows, not executed Go parity. Only these two POST routes are covered. The existing questionnaire implementation is outside this review.

## Trace and eligibility

[Router](../../../cmd/server/router.go#L1767) registers both routes in the Auth/RefreshCloudFrontCookies group, without workspace membership or human-only middleware. [Auth](../../../internal/middleware/auth.go#L37) accepts its configured credential paths; cookie writes require session-bound CSRF (403 `CSRF validation failed`), missing authorization is 401, invalid credentials are 401. Do not infer anonymous waitlist support. Handler context must contain a user ID. Neither handler requires a workspace, questionnaire, runtime, invitation, matching account email, nor uncompleted onboarding. Workspace UUID is validated only as an analytics dimension, not authorization.

[Completion handler](../../../internal/handler/onboarding.go#L43) accepts optional completion_path and workspace_id strings. Allowed path dimensions: full, runtime_skipped, cloud_waitlist, skip_existing, invite_accept; missing/other values map to unknown. Empty body is legal. Positive ContentLength triggers one JSON Decode; unknown fields and trailing JSON are not explicitly rejected, unknown-length bodies are skipped. UUID errors are 400 `invalid workspace_id`; decoding errors are 400 `invalid request body`.

[Waitlist handler](../../../internal/handler/onboarding.go#L316) requires decoded email; trims and lowercases the entire value, caps UTF-8 byte length at 254, then uses Go net/mail.ParseAddress. Display-name mailboxes can pass; do not substitute a strict bare-address regex and claim parity. Reason is trimmed and limited to 500 UTF-8 bytes, blank becomes NULL. Validation order is decode, missing email, email length, email parse, reason length. Exact error fixtures are in the adjacent JSON.

## Persistence, response and events

[SQL](../../../pkg/db/queries/user.sql#L50): completion reads GetUser then MarkUserOnboarded preserves onboarded_at via COALESCE and always updates updated_at. Either query failure returns 500 `failed to complete onboarding`. Waitlist overwrites cloud_waitlist_email/reason and updated_at, leaving onboarded_at unchanged; query failure returns 500 `failed to join waitlist` ([SQL](../../../pkg/db/queries/user.sql#L104)). Missing rows produce these database errors rather than a dedicated 404.

Both return 200 with the complete [UserResponse](../../../internal/handler/auth.go#L71), including explicit nulls and questionnaire fallback {}, without waitlist fields. Avatar URLs may be resolved by the response helper; fixtures use null. Error bodies use {"error":"message"}; middleware http.Error adds a newline. Fixtures assume a valid session unless testing authentication, and a fixed database clock; database-failure cases require otherwise valid input.

[Events](../../../internal/analytics/events.go#L584): first observed completion emits onboarding_completed with user/workspace IDs, source onboarding, completion_path, joined_cloud_waitlist and onboarded_at SetOnce. Waitlist emits cloud_waitlist_joined with user/source and has_reason on every successful update; raw reason/email are not event dimensions. [RecordEvent](../../../internal/metrics/business_events.go#L276) invokes configured Capture and local metrics; neither event is a realtime business broadcast. No runtime provisioning, agents, model execution, email delivery, invitation acceptance or workspace creation occurs here.

There is no encompassing completion transaction or outbox: the read/update race can duplicate first-completion telemetry, despite the handler comment. SQL timestamp idempotence does not prove exactly-once analytics. Event delivery is not coupled to persistence or rolled back on capture failure. No business realtime outbox is required for these routes. If future analytics needs durable delivery, use an atomic first-transition claim plus transactional event row and idempotent delivery; this is a new guarantee, not observed parity.

## Frontend and Python boundary

[API client](../../../../packages/core/api/client.ts#L1203) calls both endpoints; [store](../../../../packages/core/onboarding/store.ts#L57) refreshes auth after completion, but discards the waitlist response. [Flow](../../../../packages/views/onboarding/onboarding-flow.tsx#L245) calls skip_existing, full and runtime_skipped. Full-path agent/chat creation occurs before completion; guide creation is a separate frontend operation. [Waitlist form](../../../../packages/views/onboarding/components/cloud-waitlist-expand.tsx#L48) submits independently and does not complete onboarding. [Workspace layout](../../../../apps/web/app/[workspaceSlug]/layout.tsx#L36) gates on onboarded_at. These callers have no explicit capability guard for these POSTs; a runtime selection UI is not a server authorization guard.

[Python capabilities](../../src/workpal_backend/auth/routes.py#L24) declares no completion/waitlist support flag. [Python principal](../../src/workpal_backend/auth/dependencies.py#L14) can be reused for development sessions and cookie CSRF; production PAT/agent authentication parity must not be claimed. [Python users](../../src/workpal_backend/auth/models.py#L7) already has onboarded_at and response fields but lacks waitlist columns. Reuse that user identity and timestamp semantics; workspace/invitation tables are unnecessary for analytics-only workspace_id and must not grant membership or accept invitations.

Concrete next boundary: implement authenticated local user completion and local waitlist persistence with migration, bounded transport, response serializer reuse, rollback on database failures, repeat/concurrency tests and no external Capture. Proposed 16 KiB body cap/413 is an intentional Python hardening difference, not a Go bound. Do not reuse the questionnaire limit as evidence that these Go handlers enforce it. Preserve existing questionnaire values without revisiting its implementation.

Local registration can truthfully return success only after its user-row write commits. Cloud provisioning, real agent/model execution, production integrations and analytics delivery remain unsupported. Any API promising those effects must reject explicitly (proposed 501 {"error":"Cloud provisioning is not supported"}, zero writes), rather than using completion or waitlist success as evidence they happened. This is a proposed unsupported contract, not an existing Go error. No runtime implementation or capability change is authorized by this document.
